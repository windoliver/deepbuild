## Why the PR says Part of, and what closes the issue

AC1's time, timer and memory limits and AC6's comparison are reference-Mac budgets. `docs/parallel-proof.md` 12a gives them to the scheduled budget window on the merged commit, and says such a PR merges as `Part of #n`. The window then closes the issue itself when three things hold: AC2 to AC5 are ticked, a task names each criterion still unticked (`archive-growth` names AC1 and AC6, `#2365.76739980` and `#2365.51dff57d`, checked against the issue's text today), and every task the commit reaches passes. This branch reaches 73 of the 149 tasks (`window-tasks.txt`). A commit the window reads INCONCLUSIVE is not measured again.

Three things stand between a merge and that close. None is code this PR can change; each is under Open.

1. On Homebrew's Node 24.22.2, which a login shell and so the window's crontab line runs, the acceptance probe reads AC1's memory rise at 68 to 69 MB against the 64 MB limit. The pass itself adds 28 to 31 MB there.
2. The AC5 redraft cannot run the new merge base's archive, so it reads BLOCKED.
3. No budget window has ever run on this Mac: no crontab entry, no log, no mark.

## Deviations

- A transcript under 1 MiB is scrubbed on the calling thread. The merge base scrubs every transcript there, whole. The thread is held for one quarter part's scrub at a time.
- A copy under 8 MiB is read once more after a restart, to hash it natively.
- A one-part copy's evidence record keeps what its put gave it, as the merge base's one copy does; it is no longer put again as text.
- A copy holds about one part, the scrub's reach and its largest unit, whatever the transcript's size; a transcript that is one line is held whole. The context a continued copy reads again is the whole lines within the reach (64 KiB, or three times the longest held value). `packages/archive/README.md` states both.
- The tests ran with `--configLoader runner`, as last round: the prescribed command cannot load the Vite config in this worktree.
