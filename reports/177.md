# #177: the layer stack for HDR output

This record names the layer stack the HDR surface uses on macOS. The issue's Scope asks for it before the stack is built. It compares the two stacks the issue names, gives the GPU and compositor cost of each at 3024 × 1964 device px, and says how the chosen one stays in step through a live resize.

**Chosen: stack A, the HDR surface beneath GPUI's layer.** Neither stack leaves the issue BLOCKED. A costs one clear quad in GPUI's frame and one full-window blend in the compositor while a view presents HDR. B costs a second full-window drawable, a scene split in GPUI and two blends. A needs two small changes to the vendored renderer, which B would need too. It also needs none of the renderer's single-opacity or zero-blend gaps closed in GPUI's own pipelines.

## The two stacks

| | A: HDR beneath GPUI (chosen) | B: HDR above an opaque GPUI base, chrome on an overlay |
|---|---|---|
| Layers while HDR shows | the content view's layer, then the HDR `CAMetalLayer` (RGBA16Float, extended linear sRGB, EDR), then GPUI's layer (BGRA8, sRGB), not opaque | GPUI's base layer (opaque), the HDR layer above it, then a transparent overlay layer for the shell, card, overlays and status colors, which exists only while needed |
| Changes to GPUI | a surface registered as a clear region draws with blending off, writing transparent (`clear_surface.rs`); the layer's opacity flag drops while a frame draws one and returns after | the scene split into a base scene and an overlay scene, each to its own drawable; a second `CAMetalLayer` that GPUI owns and sizes; the clear region still needed on the overlay |
| Extra memory | none in GPUI (the HDR surface's own slots: 8 B per px, 47.4 MB at 3024 × 1964) | the overlay drawable's slots: 4 B per px, 23.7 MB at 3024 × 1964, times the drawable count (3), 71.2 MB, plus the HDR surface's |
| GPU per frame, GPUI | one quad over the view, blending off: below 0.01 ms (measured as the GPUI ledger's frame time with HDR on and off, below) | a second render pass and present for the overlay; GPUI's batches split by layer, so text and quads above the view draw in a pass of their own |
| GPU per frame, the HDR pass | one full-screen pass reading the slot and the linear target, writing f16 (measured below) | the same |
| Compositor per frame | GPUI's layer no longer opaque: one full-window blend of GPUI's layer over the HDR layer, about 3024 × 1964 × (4 + 8) B = 71 MB read, 24 MB written per composite | two blends (overlay over HDR over base), about 3024 × 1964 × (4 + 8 + 4) B = 95 MB read per composite, and the base can't be skipped where the view covers it |
| Live resize | one Core Animation transaction per frame holds both changes, see below | three layers to keep in step, two of them GPUI's own |
| HDR off or closed | GPUI's layer alone, opaque, as at the merge base | the overlay layer removed, the base alone, as at the merge base |

The renderer's opacity is one flag for the whole layer, and it has no zero-blend pipeline. A makes the flag follow the frame: while a frame draws a clear region the layer is not opaque, and the first frame without one makes it opaque again. That is the cost the issue warns of, a non-opaque window every frame, but only while a view presents HDR. The clear region is one pipeline with blending off, drawn through GPUI's existing surface path, so no new primitive enters GPUI's scene.

## How A stays in step during a live resize

- The UI thread places the HDR layer at the view's rect in the same frame callback in which GPUI draws the clear region over it. `HdrLayer::place` sets the frame inside `CATransaction` with actions disabled, so the layer never animates to its new frame.
- GPUI resizes its drawable and presents with `presentsWithTransaction` during a live resize (`vendor/gpui-pre-macos/src/window.rs`). Its present and the layer's new frame then land in one Core Animation commit.
- The HDR surface's drawable takes its new size on the render thread for the next frame. Until then the layer shows its last drawable stretched to its new frame (`contentsGravity = resize`). The layer's edge is always where GPUI's clear region is; only the content inside lags, by at most one frame.
- The fixture's capture composites GPUI's drawable over the HDR layer's frame and contents as Core Animation holds them. `tests/acceptance/177/ac4-layers.live.test.ts` reads 20 lines across the view's edges in each of 60 frames and allows at most 1 device px between the chrome and the HDR surface. The planted `surface_resizes_late` places the layer a frame late and fails.

## Measurements

These are headless readings on this Mac17,10 (M5 Max), Nov 15, 2026, at load about 170 to 300, from `deep-gpu run`'s `view3d` with `timings` on:

- the lamps scene from `tests/acceptance/177/helpers.ts`;
- 3024 × 1964;
- 60 frames;
- the stub display at headroom 4;
- medians of frames 10 to 59.

They are readings, not the budget run. AC6 judges on the reference Mac, unloaded, in the app's real window.

| Pass | First pass | Curve once | Skips dark pixels (shipped) |
|---|---|---|---|
| `scene3d.hdr` | 0.825 ms | 0.771 ms | 0.353 ms, and 0.081 ms in the run where the GPU was less contended |
| `scene3d.output`, same run (for scale) | 1.086 ms | 1.090 ms | 1.083 ms; 0.302 ms in the less contended run |

The hill-climb:

1. **First pass.** It read the slot (4 B), the covered mask (1 B) and the linear target (8 B), wrote 8 B, and ran the curve three times a pixel.
2. **Curve once.** The SDR curve is evaluated once and the rolled-off curve is skipped where something drew over the scene. The pass is bound by memory bandwidth, so this saved little.
3. **Skips dark pixels (shipped).** Only a pixel bright enough to reach the curve's shoulder changes with the headroom:
   - for filmic, none;
   - for `none`, where the slot clipped;
   - for neutral, above its knee;
   - for AgX, from 0.05 up (any channel past the toe keeps an output channel above 0.15 through the outset).

   A darker pixel keeps the slot's value without reading the linear target. On the lamps scene that is most of the frame. The pass now reads 5 B and writes 8 B there, and costs about a quarter of the output pass.

In the window, HDR on also saves GPUI's sample of the 24 MB slot into its drawable, since GPUI draws a clear quad there instead. AC6 nets the pass against that saving.

If a scene that is bright everywhere misses 0.2 ms on the reference run, the next step is to write the HDR target from the output pass as a second color attachment. The pixels the after-finish passes draw over would then be copied from the slot over the rects they cover.

## Live, on the real display

These runs were on Nov 15, 2026, on this Mac17,10 with its XDR display, the screen unlocked and held awake. Its thermal state was "fair" and the load was 30 to 240, so every timed verdict reads INCONCLUSIVE by the reference conditions. The readings are below.

**The stack.** `deep-app --hdr` with the lamps and `hdr: auto` presents through:

- an RGBA16Float layer in `kCGColorSpaceExtendedLinearSRGB` with EDR, beneath GPUI's BGRA8 layer, which is non-opaque while it shows;
- the display's current headroom, which reads 1.2 at the first frame and rises to 5.49 within 0.4 s, every step arriving as `NSApplicationDidChangeScreenParametersNotification` (5 posts, 6 reads);
- a surface peak that follows the headroom.

**AC4, live** (`ac4-layers.live.test.ts`): 4/4. With HDR off, and after the view closes, the window's layers equal the merge base. A 60-frame resize keeps the chrome and the HDR surface within 1 device px. Both planted programs fail.

**AC6** (`ac6-budgets.live.test.ts`):

- A posted headroom takes effect by frame 122 in 5 of 5 runs.
- The planted per-frame read is caught.
- The budget run's added p95 per frame, HDR on against off, is GPU [0, 0, 0.86, 0, 0] ms and CPU [0, 0, 0, 0, 0] ms. Its verdict is INCONCLUSIVE because of the thermal state and the load.

Two changes got the budget there:

- **The HDR surface presents without waiting for the refresh.** A pass into a drawable that waits for vsync holds the GPU until the display lets the drawable go. The HDR pass read 2.20 ms that way and 0.41 ms without, while the output pass in the same frame read 1.81 ms. The window is composited, so Core Animation still shows each frame on the refresh. The resize test passes with it.
- **The layer is placed only when the view's rect changes.** Placing it in a Core Animation transaction every frame cost the UI thread 0.035 ms.

**AC5** (`envelope` with `screen: main`, `hdr: auto`, called directly with a 3 s run, since the test stops at the thermal state first):

- `hdr: {state: on, headroom: 4.36}`;
- input on screen at p95 1.94 frames in each of 5 runs, against a limit of 2, at the display's own 120 Hz.

It needed four changes:

- the process's window became an accessory app's, and its events are dispatched until AppKit marks it visible (wgpu acquires nothing from an occluded window);
- the surface is configured before the headroom is read;
- events are dispatched before each read of the headroom;
- input is timed on the main display's refresh.

On this Mac the current headroom reads 1.2 before anything asks for EDR, because the panel isn't at full brightness. So the planted `auto_waits_for_headroom` would turn HDR on here too. That test can only fail as planted where the current headroom starts at 1.
