# #177: the layer stack for HDR output

This record names the layer stack the HDR surface uses on macOS. The issue's Scope asks for it before the stack is built. It compares the two stacks the issue names, gives the GPU and compositor cost of each at 3024 × 1964 device px, and says how the chosen one stays in step through a live resize.

**Chosen: stack A, the HDR surface beneath GPUI's layer.** Neither stack leaves the issue BLOCKED. A costs one clear quad in GPUI's frame and one full-window blend in the compositor while a view presents HDR. B costs a second full-window drawable, a scene split in GPUI and two blends. A needs two small changes to the vendored renderer, which B would need too. It also needs none of the renderer's single-opacity or zero-blend gaps closed in GPUI's own pipelines.

## The two stacks

| | A: HDR beneath GPUI (chosen) | B: HDR above an opaque GPUI base, chrome on an overlay |
|---|---|---|
| Layers while HDR shows | the content view's layer, then the HDR `CAMetalLayer` (RGBA16Float, extended linear sRGB, EDR), then GPUI's layer (BGRA8, sRGB), not opaque | GPUI's base layer (opaque), the HDR layer above it, then a transparent overlay layer for the shell, card, overlays and status colors, which exists only while needed |
| Changes to GPUI | a surface registered as a clear region draws with blending off, writing transparent (`clear_surface.rs`); the layer's opacity flag drops while a frame draws one and returns after | the scene split into a base scene and an overlay scene, each to its own drawable; a second `CAMetalLayer` that GPUI owns and sizes; the clear region still needed on the overlay |
| Extra memory | none in GPUI (the HDR surface's own slots: 8 B per px, 47.4 MB at 3024 × 1964) | the overlay drawable's slots: 4 B per px, 23.7 MB at 3024 × 1964, times the drawable count (3), 71.2 MB, plus the HDR surface's |
| GPU per frame, GPUI | one quad over the view, blending off: below 0.01 ms (measured as the GPUI ledger's frame time with HDR on and off, below) | a second render pass and present for the overlay; GPUI's batches split by layer, so text and quads above the view draw in a pass of their own |
| GPU per frame, the HDR pass | one full-screen pass reading the slot and the linear target, writing f16 (measured below) | the same |
| Compositor per frame | GPUI's layer no longer opaque: one full-window blend of GPUI's layer over the HDR layer, about 3024 × 1964 × (4 + 8) B = 71 MB read, 24 MB written per composite | two blends (overlay over HDR over base), about 3024 × 1964 × (4 + 8 + 4) B = 95 MB read per composite, and the base can't be skipped where the view covers it |
| Live resize | one Core Animation transaction per frame holds both changes, see below | three layers to keep in step, two of them GPUI's own |
| HDR off or closed | GPUI's layer alone, opaque, as at the merge base | the overlay layer removed, the base alone, as at the merge base |

The renderer's opacity is one flag for the whole layer, and it has no zero-blend pipeline. A makes the flag follow the frame: while a frame draws a clear region the layer is not opaque, and the first frame without one makes it opaque again. That is the cost the issue warns of, a non-opaque window every frame, but only while a view presents HDR. The clear region is one pipeline with blending off, drawn through GPUI's existing surface path, so no new primitive enters GPUI's scene.

## How A stays in step during a live resize

- The UI thread places the HDR layer at the view's rect in the same frame callback in which GPUI draws the clear region over it. `HdrLayer::place` sets the frame inside `CATransaction` with actions disabled, so the layer never animates to its new frame.
- GPUI resizes its drawable and presents with `presentsWithTransaction` during a live resize (`vendor/gpui-pre-macos/src/window.rs`). Its present and the layer's new frame then land in one Core Animation commit.
- The HDR surface's drawable takes its new size on the render thread for the next frame. Until then the layer shows its last drawable stretched to its new frame (`contentsGravity = resize`). The layer's edge is always where GPUI's clear region is; only the content inside lags, by at most one frame.
- The fixture's capture composites GPUI's drawable over the HDR layer's frame and contents as Core Animation holds them. `tests/acceptance/177/ac4-layers.live.test.ts` reads 20 lines across the view's edges in each of 60 frames and allows at most 1 device px between the chrome and the HDR surface. The planted `surface_resizes_late` places the layer a frame late and fails.

## Measurements

Headless, on this Mac17,10 (M5 Max) at load about 170 to 210, Nov 15, 2026: `deep-gpu run`'s `view3d` with `timings` on the lamps scene from `tests/acceptance/177/helpers.ts`, at 3024 × 1964, 60 frames, with the stub display at headroom 4, medians of frames 10 to 59, two runs each way. These are readings, not the budget run. AC6 judges on the reference Mac, unloaded, in the app's real window. That run hasn't happened yet because the screen was locked.

| Pass | hdr auto | hdr off |
|---|---|---|
| `scene3d.hdr` | 0.771, 0.772 ms | not run |
| `scene3d.output` (for scale) | 1.090, 1.098 ms | 1.089, 0.687 ms |
| `scene3d.geometry` | 0.930, 0.932 ms | 0.930, 0.597 ms |

What these show:

- The HDR pass reads 13 B and writes 8 B per pixel. It runs at about the output pass's rate per byte, so it is bound by bandwidth, not ALU. The figure above is after it evaluates the SDR curve once and skips the rolled-off curve on drawn-over pixels; it was 0.83 ms before that.
- In the window, HDR on also saves GPUI's sample of the 24 MB slot into its drawable. AC6 compares the whole frame with HDR off, so the pass's cost is netted against that saving.
- If the reference run still misses 0.2 ms, the next step is to write the HDR target from the output pass as a second color attachment. That adds 8 B per pixel of writes and no reads. The pixels the after-finish passes draw over would then be copied from the slot over the rects they cover, which the CPU already knows.
- The compositor's cost (stack A's one extra blend while HDR shows) can only be read on the real display; the live fixture's frames report GPUI's ledger, not the window server's.
