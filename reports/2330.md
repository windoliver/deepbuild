An independent read-only review also identified four **open production risks**;
these are source reasoning, not check results, and the candidate is not ready:

- `waitForStop` treats every verification `connect()` rejection as success,
  including a hello timeout capped by the remaining deadline. A live listener
  whose hello arrives after that short interval can therefore be called stopped.
  Only a proven quiet/closed socket should satisfy the stop; deadline expiry
  must remain failure, not evidence of absence.
- A clean EOF before a complete verification hello does not settle `connect()`'s
  pending line wait, so a shutdown race can retain its 2 s timer. It needs a
  regression with a peer that accepts and closes during that handshake.
- `stopIfRunning` still swallows the new stop-wait timeout, so installed stop can
  print success with a live hub; setup undo uses this path too. This predates the
  patch but remains an unresolved scope edge.
- The actual server destroys client sockets before core shutdown and process
  exit. The stand-in exits with its sockets, so it does not prove the real hub's
  exit ordering. A stop-request connection needs to represent completion without
  retaining unrelated pending calls (the #823 unavailable-on-stop rule).
