## Why the base side rebuilds every run

cargo's own reasons, from run b (`b-reasons.txt`, `b-build-workspace-deep-show-reason.txt`):

1. **deep-show's build script watches the deep-app folder.** `crates/deep-show/build.rs:103` prints
   `cargo:rerun-if-changed=<folder>` for every crate folder deep-show depends on, `crates/deep-app` among them. While
   the checks run, gpui-shell writes the gitignored `gpui-kit.d.ts` and `jsconfig.json` into
   `crates/deep-app/panels/*/` (`.gitignore:16–17`). At the next run's start, perf's replace deletes them (b: `wrote
   2 files, deleted 71`). In b, cargo marked deep-show `stale: changed "…/base/copy/crates/deep-app"` 8 times and
   compiled it 10 times: once for `cargo build --workspace` and once for each test feature build of deep-show. This is
   not the kit-ledger exception of AC2.
2. **Workspace clippy fails on this commit, so its unfinished units never get a fingerprint.** `cargo clippy
   --workspace --all-targets --locked -- -D warnings` stopped with errors in every run. On `61aa8eb0` the errors were
   `result_large_err` and `type_complexity` in `crates/deep-canvas-sandbox/src/link.rs:331` and
   `chunks_exact_mut` in `crates/deep-canvas-marks/src/light.rs:226` (`b-clippy-workspace.txt`). The units clippy
   had not finished have no fingerprint file (`fingerprint error … failed to read`, 1,627 lines in b), so the next
   run checks them again. In b that was 47 `Checking` lines, mostly third-party crates, plus 7 `Compiling` lines for
the build scripts and proc macros under them (gpui-pre and its macros, strum_macros, phf_codegen and others). Latest main (`2fb3fe99`) has changed
   `link.rs`. Whether clippy passes there was not read.

The first cause holds on any run that loads panels, so a second worktree's 0 cannot be read in this repository
until deep-show stops watching a folder the checks write into. The second cause depends on the commit.

## Test processes outlive the allowance

perf's timeout stops only the process group it measures. Each run's vitest started its own group, and those groups
kept running in the kept copy after the verdict. They made 223 to 331 further base-copy cargo calls per run
(`base-units.txt`, the "after" column). `run-all.sh`'s check for them (`lsof +D` on the kept copy) found the copy
idle every time (`*-meta.txt`), so it missed them. a1's and a2's groups were found by hand before a3 and stopped by
PGID. a4's group ran on through all of run b and was stopped by PGID after b, together with b's own.

So b ran beside a4's leftover tests, and its wall time and load carry that. Its deep-show rebuild does not come
from them. cargo's reason compares deep-app's newest change, 11:03:27Z, with deep-show's build output, 10:36:48Z.
11:03:27Z is perf's own replace at b's start (`b-perf.stdout.txt`, 11:03:29Z).
