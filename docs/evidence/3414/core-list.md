# #3414: the one list of what the core holds

Building blocks (docs/technical-design.md), its whole paragraph; the list is its first sentence:

The core is the part of DeepBuild that nothing replaces or extends, and it holds six parts: the record, the contract (the shapes and APIs it publishes by version, with its two rules and the adapter contract), capabilities, the trusted path, the floor and verdicts, and asks. Every outside call DeepBuild itself makes, from the hub or a plug-in, goes through capabilities: a grant, a quota and secrets only by handle, with the supervisor enforcing the grant of every process it starts. That covers a GitHub status or comment, a channel's message and every source read. Every call capabilities refuse, for its grant, its quota or its schema, is recorded as a `capability.refused` event, with the writer taken from the caller's connection, never from the call's arguments or headers, the grant clause or limit it broke, and a digest of the call, never its values. An agent's own calls to its model provider aren't capability calls: they're the agent's, made with its own sign-in, even in a job DeepBuild's runner starts. Nor are a shared piece's reads in the web player, which fetches only the public sources the piece declares, from the viewer's browser with no credential. The two rules are: *PASS needs real runs, at the depth the claim needs, of checks its own agent didn't write*; and *each question gets one answer, or its announced default at the deadline*, which is no for anything irreversible and can always be undone. A trusted ring ships with it: the app shell, the canvas that draws everything on screen, the device and media gate, the supervisor and the installer, the only code beyond the core that no plug-in can replace. The canvas core inside the ring is built like the hub: a small core, canvas modules as its parts, and data packs and the extension host as its only extensions; the programs, libraries, providers and validators a pack carries run only under `sandbox@1`, the first-party sandbox module, and the operators it writes in the WGSL subset are lowered to the core's own steps. Canvas modules are ring code; plug-ins can't replace or extend them. The done gate is an extension, and so are the resolvers and each agent's adapter: plug-ins on the contract. The gate's floor stays in the core whatever gate is installed (see [First-party extensions](#extensions)), so the gates the core holds are that floor, never the done gate. Agents and extensions work with the blocks below and nothing else. Every block changes the same way: proposed, checked, approved, recorded, and rolled back with a compensating event. Blocks are meant to be composed; see [Composition](#composition). The skill and the MCP tool descriptions are generated from this table, and a test fails when they drift apart. The skill carries only what the tools can't teach, when to use each block and what it never does, and never a tool's parameters, which agents read from the tool's schema. For canvas work it also carries the order to work in: start from a piece recipe or a kind `deep_kinds` lists, check the document before rendering it, render small and read the issues, fix by patch, and render in full only once the numbers pass; it judges by numbers, never by eye. When no kind or field does what a piece needs, the agent raises an open item with `deep_open_item` naming what's missing, instead of approximating it.
