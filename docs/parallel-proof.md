# DeepBuild: parallel proof

> How this repository's own proof tooling shares two machines between many agent sessions without letting one session's load, build or stale copy change another's verdict. It covers what runs on the Mac and what on the Spark, fixed-path build workspaces called bays, the cost cuts inside one proof run, a per-machine throttle table, the split of the unit lane's `alone` block, remote lanes, machine hygiene, how the tooling issues are shaped, and the budget windows that measure every merged commit on a reference Mac. It is the design the proof tooling issues T0–T10 build on.

This is the repository's tooling, not the product. The product's own lease for builds in users' repos is #1015, and nothing here imports it. The checks and their verdicts are those of [How we know version 0 works](technical-design.md#how-we-know-version-0-works); this page changes where and when they run, never what they accept. Each step's issue holds its criteria; this page holds the reasons.

## 1. Goal

Many sessions work in this repository at once, each in its own worktree, and each proves its change before it merges. Today every proof starts cold, every lane runs on the session's own machine, and two proofs on one machine turn each other's budgets INCONCLUSIVE. The goal is shorter proofs and budgets that count, with no verdict weaker than today's except where a step says so, names the trust it gives up, and records it.

## 2. Measured baseline

Readings from the Mac and the Spark before any tooling change, which the steps are measured against:

- **Load.** With nothing building, the Mac sat at a 1-minute load of 14–18 with swap 97% used. A budget refuses to count at a load above the core count (invariant 2), so at that load every budget reads INCONCLUSIVE. This is the largest slowdown measured, and hygiene (section 9) comes first for it.
- **Worktrees.** 47 worktrees on the Mac had merged branches. Several worktrees on open branches held large `target/` folders.
- **Cold copies.** The proof lane makes a cold copy per use (the base, the change, each twin, crash, replay) and runs `npm ci` plus a 26-package build in each. Copies made by git archive start with no `target/`, and the preflight deletes `CARGO_TARGET_DIR`.
- **perf.** perf keys its kept copies by worktree path, so every new session worktree starts both sides cold.
- **The `alone` block.** The unit lane's `alone` block runs 125 entries one at a time, 557 s in the recorded run.
- **Stryker.** Each mutant rebuilds all 26 packages.
- **The Spark.** 20 cores and 121 GB of memory, running nothing for a Mac session. 21 of the 27 crates build there.

## 3. Placement: what runs where

The Mac is the only machine whose results can count as budgets, and the only one that runs macOS and Metal. The Spark is Linux on aarch64 with most of the cores and memory. Placement follows from that:

| Work | Runs on | Why |
|---|---|---|
| Budgets, perf, timing gates | The reference Mac, in a budget window (section 12a) | A budget counts only on a reference Mac's fingerprint, at load below its cores |
| GPU, Metal and macOS-only tests | The Mac | The Spark has neither |
| Tests that reach a platform-branching source | The Mac, always, beside any Spark run | A Spark pass says nothing about the macOS branch (section 8) |
| The lint verdict | The Mac | A Spark lint record is a reading, never the lint verdict |
| Unit lanes, `cargo test`, proof lanes and Stryker for a Mac session | The Spark, by remote lane, once T7 and T8 land | Cores and memory, without loading the Mac |
| Docs-only changes | The Mac | Nothing to build |

A Spark `cargo test` is never PASS on its own: its record lists the tests absent by platform, by comparison with the Mac's reference list (`cargo test -- --list` per target, written into the Mac's evidence record), and the lane is INCONCLUSIVE (platform). First the whole workspace has to build and test on Linux aarch64 (T8): deep-app and its five dependents fail because `image` sits in deep-app's macOS-only dependencies while `picture()` uses it unguarded, `lsof` is hardcoded at its macOS path, and deep-hook's `O_NOFOLLOW` is the x86_64 value, so on aarch64 its symlink refusal does nothing.

## 4. Build reuse: fixed-path workspaces, not relocated targets

Moving a warm `target/` to a new path does not work: a target keeps the old path baked in through `CARGO_MANIFEST_DIR` and `CARGO_BIN_EXE_*` (21 files in 10 crates use them), so a relocated target would run the base's binaries against the change's tests. Instead the path stays fixed and the tree moves into it.

A **bay** is a fixed-path workspace, `~/deepbuild-bays/<k>/`, claimed in pairs: one bay for the base and one for the change. The Mac has one pair and the Spark three, claimed through the throttle's `bay pair` class (section 6), whose grant index names `<k>`. The rules:

- **Replaced in place.** Each use writes only the files whose bytes differ from disk, from the run's exact tree: a git archive of the tree hash, the bundle of uncommitted changes and the untracked non-ignored files, with all three hashes recorded. Files absent from the tree are deleted, and no mtime is ever backdated, so cargo and tsc see every change. Comparing blob IDs instead of bytes is a planted wrong program the tests show failing.
- **What stays.** Only `target/` and `node_modules/` are kept across runs. `.git` is recreated each run, with `alternates` to the root's common directory, and `packages/*/dist` is deleted before the workspace build.
- **One role each.** The base bay holds the merge base, plus the before lane's overlaid test paths; the change bay holds the change and, in turn, each twin. Crash and replay reuse the pair in the same roles. A bay never flips between base and change, and before every use it is replaced to that use's exact recipe, written into the record per use.
- **Its own target.** A bay build or test runs with `CARGO_TARGET_DIR` removed from its environment, so it always writes `<bay>/target`.
- **`undoBuild`.** In a bay, it skips `.git`, `target/` and `node_modules/`, and its copy-back skips files whose bytes match.
- **The seal.** At release, the bay records a stat listing (path, size, mtime in ns, inode) of all of `target/` and `node_modules/`, plus the tree hash. At claim, any mismatch deletes both and builds cold, and the record says so. `npm ci` is keyed on the lock file's bytes and a post-install marker.
- **Kept builds** (#3019). What a use's workspace build wrote outside `.git`, `target/` and `node_modules/` (the packages' `dist`) is kept per machine under `~/deepbuild-bays/cache/<key>/`, one entry per key, each file a blob named by its SHA-256. The key is exact: the bay's path, a hash of every file in the bay outside those three folders as the build starts (so a twin's overlay, laid before its build, counts, and the base's overlay, laid after it, doesn't: every change at one merge base shares the base's workspace build on one bay), the tools as each reports itself where it runs (node, npm, rustc, cargo, cc, pkg-config, a compiler `CC` or `CXX` names, through any wrapper; on macOS swiftc and the SDK, elsewhere ldd), the locks' bytes and the lock `node_modules` was installed from, cargo's config in `CARGO_HOME` and every folder above the bay, npm's user config and the global config the running npm reads, every package in any `node_modules` above the bay by its `package.json`, the build environment (cargo's, rustc's, the C toolchain's as the `cc`, `bindgen` and `pkg-config` crates read it, include and library paths, node's and npm's but npm's per-worktree `npm_config_local_prefix` and cargo's jobserver `CARGO_MAKEFLAGS`, the project's own `DEEP_*` variables (a package's build script may read one, as `pi`'s reads `DEEP_HUB_PLANT` through the hub) but the lane's per-run lease, paths and settings and a hub job's tokens and lease (one left unlisted costs only reuse), every variable a `build.rs` under `crates/*/` or `vendor/*/` names in `rerun-if-env-changed`, and the bytes of a file such a variable names) and the hash of the lane code. A later use whose key matches lays the entry back instead of building, after hashing each copied file against the entry; a file that no longer hashes as stored, or an entry that can't be read whole, is not used: the entry is removed, the use builds fresh, and its `BUILD` line says why. Each `BUILD` line names the role, the tree hash and the key (null when it couldn't be worked out), and says `reused`. Only a build that succeeded is kept, and only when the build only added files, each in a workspace package's `dist` (`packages/<name>/dist/`), which the bay pruned: a file that was there before and changed, one deleted, one elsewhere, or a change at the top of `node_modules/` or `target/`, which a keep can't carry, is another writer's, such as a hub a test left running. The snapshot it is compared to is taken before the key's files are read. A build is not kept when a tool was stopped or couldn't start before it answered, or a lay failed halfway; a lay that fails halfway takes back what it laid first (a laid `.tsbuildinfo` would leave `tsc` nothing to emit), and a bay where that fails doesn't build, so its role is blocked; and an entry holds no input but its key, so no secret of the environment is written. Entries go oldest first, by when they were stored, once the bytes under the cache pass `DEEP_BUILD_CACHE_BYTES` (default 10 GiB), which holds before each read and after each write; `0` is no cache and empties it; a value that isn't a whole number is no cache for that run and leaves the cache as it is. A failure of the cache never fails the proof, but for a lay that can't be taken back: the bay builds fresh and says why. Test binaries are not kept: building them every use keeps `target/` warm for a test's own `cargo` build, and in the same bay that build is incremental. A second run at one merge base reuses the build only on the same bay, so on the Spark's three pairs only a run on the same pair does.
- **Who gets one.** Only a proof rooted in a worktree of the machine's repository, with no ancestor holding a pair. `tests/proof.test.mjs`, the #569 scene proofs and other test-started proofs keep temporary copies. A lock holder's death releases its bay.

There is no fallback flag: rollback is reverting the PR.

### Trust boundary

Bays are weaker than today's proof lane, and equal to today's perf kept copies. A temporary checkout cannot carry anything from a previous run; a bay carries its `target/` and `node_modules/`, guarded by the seal. The record binds the sources, not the target. Kept builds are as strong as the seal and no stronger: an entry is checked against its own `entry.json`, which lies beside it, so a process that can write `~/deepbuild-bays` can plant a build for a key it works out, and unlike a seal, which a claim consumes, an entry serves every later use with that key until it is evicted. Each `BUILD` line says when a verdict rests on one. This replaces #569's "runs on the merge base in a temporary checkout" for the base copy, and the record names the bay's seal check so the weaker trust is visible on every verdict that used it. `bays.mjs` joins the guard's list of the proof lanes' own code from its first PR.

### Dependencies shared across worktrees: sccache, per machine

Twenty worktrees on the Spark each build the workspace cold into their own `target/`. What they can share, and what they can't:

- **Not a shared `CARGO_TARGET_DIR`.** One target directory for every worktree has the relocated target's flaw above, across branches: `target/debug/<bin>` is rewritten by whichever worktree built last, with `CARGO_MANIFEST_DIR` and `CARGO_BIN_EXE_*` pointing into it. `parity.mjs`, `agent-eval-run.mjs`, the `alone` block (section 7) and the 70–80 acceptance files that spawn `cargo` read `<worktree>/target/debug/<bin>`, which a shared target leaves empty; `DEEP_BIN_DIR` will cover a lane's own runs once T4 lands, and an acceptance file only once its blind redraft reads it. Cargo's target lock would also hold every worktree's build behind every other's, under the throttle. The preflight and the bays delete the variable for these reasons, and keep doing so.
- **sccache as the machine's `rustc-wrapper`.** A dependency from the registry or a git source compiles to the same bytes in every worktree: same source, same flags, same toolchain. sccache keys each `rustc` call on those and writes the cached artifact into the worktree's own `target/`. The workspace's crates compile incrementally, which sccache passes through, so each worktree's own crates and binaries are built in place and found where everything above reads them; `DEEP_BIN_DIR`, the bays and the throttle are untouched. The setting is the machine's, in `~/.cargo/config.toml`, never the repository's `.cargo/config.toml`: a machine without sccache would fail every build. The Spark has run this since 2026-11-07, re-applied after the 2026-11-02 disk cleanup removed the line with the cache. A reference Mac may run sccache too (#3239): its budgets are bare by their scripts' own setting, never by the machine's (below), so the cache and its two config files go on a Mac by hand from a login shell, as here, and no script installs them.

  ```toml
  [build]
  rustc-wrapper = "sccache"
  ```

  The cache, under `~/.cache/sccache`, is capped at 40 GiB in `~/.config/sccache/config` (sccache's own default is 10 GiB; the full dependency set in both the check and the codegen form needs more):

  ```toml
  [cache.disk]
  size = 42949672960
  ```

- **The server is the machine's, so start it as the owner.** Cargo's `sccache` calls are clients of one server per machine, which the first client starts with its own environment and which then serves every later client from that environment's `HOME`. On 2026-11-07 a test's child with a temporary `HOME` under a session's scratchpad started it: the machine's server then kept its cache in that scratchpad at the 10 GiB default, with the owner's config and warm cache unread. A server reads its config only at start. So after editing the config, and after any session could have started one, the owner stops and restarts it from a login shell, kept alive so no child's environment replaces it:

  ```
  sccache --stop-server; SCCACHE_IDLE_TIMEOUT=0 sccache --start-server
  ```

- **What defeats a hit: `CARGO_TARGET_DIR` in the environment.** sccache hashes every `CARGO_*` variable the compile sees, and cargo passes that one through. A build whose environment names a target directory misses on every crate, even the same worktree rebuilding the same leaf crate into a second directory; the `--target-dir` flag, which cargo doesn't export, is harmless. In this repository `perf.mjs`, `benchmark.mjs`, `api-surface.mjs` and `budget-window.mjs` set the variable, so their cold builds never hit and never seed; the bays delete it, so theirs do. The machine's counter read 9 Rust hits in 1,802 compiles between 22:36 and 23:00 on 2026-11-07, under the scratchpad server above; how much of that is the variable and how much is cold builds nothing had seeded needs the server's log (`SCCACHE_LOG`), a reading not yet taken.
- **Off where a build must be bare.** `RUSTC_WRAPPER=` (empty) in a child's environment is no wrapper, over the config, and `CARGO_BUILD_RUSTC_WRAPPER=` likewise; `tests/acceptance/1016` and `1017` set them for their cold builds. A budget is bare by its script's own setting: `perf.mjs`, `budget-window.mjs`, `benchmark.mjs` and `preflight.mjs` start every cargo with `RUSTC_WRAPPER` empty (#3239), so the preflight's checks with their builds, perf's copies and the window's sides never use a cache the machine has, and every other build on the machine may. `594` is bare by pointing `CARGO_HOME` at an empty folder. `1117`–`1119` only delete the variable, so with the config in place their builds run under the wrapper, which changes how long a compile takes, never which crates compile, and their criteria count crates. cargo-mutants and cargo-semver-checks run under the wrapper like any build. Toggling the wrapper on a warm `deep-hook` build recompiled 0 units either way (a reading, 2026-11-07), so a warm worktree stays warm the day the setting lands.
- **Readings** (Spark, 2026-11-07, `cargo test --no-run -p deep-text-gpui`, 876 crates, each build into an empty target; 1-minute load 37–58 throughout, so the wall times are readings against each other, never budgets). 532 of each build's compiles are cacheable; the other 129 are binaries, proc-macros and the workspace's incremental crates.

  | Build | Target named by | Wall | Rust compiles from the cache |
  |---|---|---|---|
  | Two detached worktrees of one commit, the first then the second | in-tree `target/` | 73 s, then 56 s | 417 of 532 on the second |
  | Three real worktrees on three branches, two lockfiles | `CARGO_TARGET_DIR` in the environment | 85, 101, 91 s | 0 of 532 on each |
  | Two of those worktrees again, two branches, two lockfiles | `--target-dir` flag | 59 s, then 66 s | 411 of 532 on each |

  The 121 misses with the flag are the workspace's and `vendor/` crates and what depends on them, whose path is in their metadata hash. The two lockfiles differed by 13 added packages outside this closure, so a branch's lockfile drift costs only the crates it changes. `cargo clippy --all-targets -p deep-hook` took 7–8 s with or without the cache: its two crates are the workspace's own, with nothing to take. A first worktree pays nothing measurable for the wrapper: without it the small builds took 7, 8 and 18 s, as with it.
- **What stays.** Build scripts' runs, proc-macros, binaries, linking and the workspace's own crates are never cached, and they are most of what a cached build still pays. Each worktree still keeps its own `target/`, so section 9's rule on idle worktrees' targets still applies. The cache is itself what a disk cleanup may delete; the next build repopulates it, and a missing cache is never a failure.

## 5. Proof-run cost cuts inside one run

Once bays exist, most of a proof run's cost is work it repeats:

- **`npm ci` only when the lock changed** (T2). Per proof run it is 0 without a lock change, 1 when the change edits the lock, and 1 more in the base bay only when the merge base moved past a lock change. Stryker's `node_modules` relink walk is skipped in a bay.
- **perf's kept copies per machine** (T3). They are keyed per machine and clone, `deepbuild-perf/<machine>-<clone>/{base,without-tests}`, not per worktree path: every worktree of a clone shares them, and another repository on the machine, such as a test's fixture, gets its own. `<clone>` hashes the clone's git directory, and `<machine>` is the first label of the machine's name, which macOS and a router's DHCP extend with a domain that changes with the network (`.local`, `.attlocal.net`). They sit under one lock for the clone on the machine, taken only under the `timed` class, and their trees are replaced by the bays' byte-compare rule. The one rebuild left on the base side is deep-show and its dependents when the canvas-kit lane rewrote `kit-ledger.json` with different bytes, and the record names it.
- **Stryker scoped to the mutated package** (T6). Per mutant, build the mutated package and its dependents, read from the reverse workspace graph: `tsc -b packages/<p>` alone builds p and its dependencies, while tests read the dependents' `dist`. `undoBuild` still restores every touched source file. A planted scope that builds the mutated package without its dependents changes the kill set; the real scope leaves the killed and survived sets equal to an unscoped reference run's.

### Binaries for tests

Test binaries are built once per run into a run-private `bin/`, named by `DEEP_BIN_DIR` (T4). The before lane sets it per side from each bay's own build, so base and change never share binaries. `childEnv` drops an inherited value before it merges its `extra` argument, so a per-side value survives and a shell's value never leaks in. `lanes.mjs` and `affected.mjs` always set it from their own build, never from the shell. This is what lets folders leave the `alone` block (section 7).

A hub finds `deep-hook` and `deep-show` only under its own checkout's `target/`, the newer of `release` and `debug`, and the before lane's copies hold no build (#2817). So when a selected test, or a helper it reaches, names the hub's or the CLI's package, each side also builds those two from its own sources and copies them into its copy's `target/debug/`, stamped newest. A whole command string such as `node packages/cli/dist/main.js hub run` names it too, and so does a test or helper inside either package. A test file the test names as a path from the checkout's root is followed as an import is, since the test may run it in a child Vitest, as #3178's meta-test runs its rows (#3293). The tests that name neither package run first, with no hub binary in the copy, and the hub's tests after them, so a test that names neither never finds them. A bay keeps `target/` between uses, so each use first removes what an earlier one put there. The mutation lane's copy gets the same before each StrykerJS run, built from the change's sources and chosen by that run's tests (#2835); when its proven tests mix both kinds, they run as two StrykerJS runs, those that name neither package first, as in the before lane. Runs in the checkout itself keep its own `target/` and only read `DEEP_BIN_DIR`.

An `affected.mjs` run builds its `DEEP_BIN_DIR` binaries before it asks for its test grant (#2820), under one `build` grant of its own that it waits for as long as for the test grant, so no test slot waits on cargo. With them it builds, in the worktree and in each shard, the `cargo build`s its untimed selected tests and their helpers start themselves, where the source writes out every argument and names workspace binaries (a `--bin` whose name is a variable counts once for each workspace binary whose own name the test's sources write, of the package it names if it names one), run as the test runs them, in that checkout's `target/`. Each runs with its test's profile: `CARGO_INCREMENTAL` and `CARGO_PROFILE_DEV_DEBUG` default to 0 where the file making the call names them, which is how the acceptance helpers default them, and stay as the run's environment has them otherwise, so the test's own build finds each unit fresh and compiles nothing. A build with other flags, a value the source doesn't write out, or a `CARGO_TARGET_DIR` written in its call is left to the test; one the run builds that fails ends the run `BLOCKED` with no test grant taken. These builds, and the run's `DEEP_BIN_DIR` builds, have no time limit, since they hold no test slot; a cold one of the largest binaries took over an hour on the Linux machine. A run whose tests build no binary takes no build grant.

## 6. Scheduling: a per-machine throttle table

Budgets refuse to count at a load above the core count, so two sessions proving at once turn each other's budgets INCONCLUSIVE. `scripts/throttle.mjs` (T5) is a host-local, flock-based lock table under `~/.deepbuild/throttle/` with four classes. The folder is the user's home from the password database, never `HOME`, so a run with a `HOME` of its own still shares the machine's table (#2744):

| Class | Mac | Spark | Holds |
|---|---|---|---|
| build | 4 | 6 | Top-level builds outside proofs: cargo build, `cargo test`, `npm run build`, clippy. The default for an unlisted command. The number is a ceiling: a build asked for under no grant is admitted by the memory rule, then takes a turn on the machine's pool (below, #3549) |
| bay pair | 1 | 3 | A counting semaphore whose grant index k names `~/deepbuild-bays/<k>/`; `bays.mjs` is its only caller |
| test | 2 | 6 | The vitest parallel block and `node --test`, and an `affected.mjs` run's admission, whose jobs then take turns on the machine's pool (below). The number is a ceiling: past the first grant, the machine's readings decide (below) |
| timed | 1 | 1 | Exclusive of every class; waits for load below the core count |

`throttle.mjs <class> [--wait <min> | --stall <min>] [--hold <min>] [--turns 0] -- <command>` acquires, runs, releases and exits with the child's status, or 128 plus the signal when the child is killed. An importable `acquire(class)` and `release(grant)` serve `proof-runs.mjs`, `preflight.mjs` and `perf.mjs`. `lanes.mjs` wraps each of its commands by this classification, and `affected.mjs` routes its own commands the same way: the workspace build, clippy and `cargo test -p` as build, the vitest block and `node --test` as test.

- **Test grants by the machine's readings (#2924).** A top-level test request is granted at once while no test grant is held. Past the first, one more starts only while fewer than the ceiling are held, the 1-minute load is below the core count, and the memory available (`os.freemem()`, `MemAvailable`, on Linux), less 24 GiB for each held test grant still settling (younger than 5 minutes, or of no known time), is still at least 24 GiB. Each run on the Spark is a unit capped at `MemoryMax=24G`. The Mac reads the memory available as `kern.memorystatus_level`, the kernel's percentage of memory free, times the machine's memory, since `os.freemem()` there counts only free pages and reads a fraction of a GiB on a busy Mac; the Mac budgets 8 GiB a run, for the 24 GiB and for each settling grant's reserve, since a Mac run's whole process tree measured 2.6 GiB (#2980). The readings are `machineReadings()`'s; a run that has just started doesn't show in the readings yet, so a burst of waiting requests can't all start on the same idle reading. A waiting request reads them again at each look. The log's `granted` entry for a test grant carries the `readings` it was decided on. The machine's table always reads the machine. A test's own table (below) reads the file `DEEP_THROTTLE_READINGS` names, a JSON `{"memory", "load", "cores"}` read again at each look, or without it decides by the ceiling alone, since its holders are a test's stubs. The variable set for the machine's table or outside a test run, or a file that can't be read as those three numbers, is `BLOCKED throttle`. bay pair keeps its fixed limit: its index names a physical bay. timed keeps its own load rule. An `affected.mjs` run's admission and a build's (both below) are decided by these rules without the load.
- **One limit per machine (#2902).** Every checkout on the machine shares the table but states its own limits, and an old branch or base-comparison tree may state fewer. Each request records the limit it was made under, and a request is served in order only while that limit has room, so the largest limit among the live waiters is the machine's. A request that records no limit comes from a checkout older than #2902 and counts as allowing one grant: once its class holds a grant, later requests are served past it, and its own code still takes a slot whenever it is first in its own view and below its own limit. A stale waiter at the head therefore holds the machine below the current code's limit no longer, though with none of its class held it is still served first, as before.
- **Inherited grants.** A held grant is exported as `DEEP_THROTTLE=<class>:<id>`. Descendants pass through for build and test. timed never passes through, unless an ancestor holds timed. `DEEP_THROTTLE` is verified against the lock table, a live holder pid and the holder's place in the requester's parent-pid chain, never trusted; a forged one is ignored and a fresh grant is requested.
- **The lease script never runs a command bare (#3238).** `scripts/lease <command>`, where a session's own build is sent to share the machine (#1015), runs its command under `throttle.mjs build`. When an ancestor holds a grant it passes through on the ancestor's grant and waits for nothing: inside an admitted run it takes no turn of the pool either (`--turns 0`, below), so a lint `affected.mjs` runs through the script under its run's grant, as a job of its own under no turn, starts at once though every token is held (section 7a); with none it asks for a top-level `build` grant and waits at most 30 minutes for it, as a lane command does (`DEEP_LEASE_WAIT` sets the wait in minutes, for tests). With no grant in the wait it prints the throttle's `INCONCLUSIVE no grant` line and exits non-zero, and the command never starts; a table it can't use reads `BLOCKED throttle`, with nothing started either. Inside the grant the command runs through `deep lease` where `deep` is on the PATH or the CLI is built, so a hub's lease table shows it under its session; with no hub, or with neither, it runs under the grant alone. So a session's build counts as one of the machine's top-level builds, admitted under the build ceiling and run on a turn of the pool (Builds on the pool, below), whether or not a hub is set up there, where it used to start at once.
- **Admission (#3221).** An `affected.mjs` run's test request is its admission: the process that asks has `DEEP_THROTTLE_RUN` set to the free disk its shards need, in bytes (section 7a's floor and 5 GB a shard, or 0 with no shard), and `throttle.mjs` takes the variable out of its command's environment. An admission is decided as a test grant is, by the ceiling and the memory rule, but not by the load, since the pool below bounds what admitted runs run; it also waits while the disk under `HOME` has less free than the bytes named. The class's ceiling bounds the admitted runs and the other test grants together. A run asked under a caller's build or test grant, as the preflight's unit lane runs one, is admitted at once, nested, and takes no slot; one asked under a turn (below) passes through on that turn, as a nested request always has.
- **Turns on one pool (#3221).** Inside an admitted run, each `build` or `test` request from a process under no turn, as each job `affected.mjs` starts, but not one made with `--turns 0`, as `scripts/lease` makes (#3238), passes through on the run's grant as before (the log's `passed`, through the run's grant, and its command's `DEEP_THROTTLE` names the run's grant), then waits for a turn: one of the machine's pool of job tokens, a core less one and at least one, the cores being a test's own table's readings' when it has them. A free token goes to the waiting job whose run's jobs have had the least time on turns so far, those ended and those in flight, and between two of one run, or two runs with the same time, to the one that asked first. A turn has no wait limit, so an admitted run never reads `INCONCLUSIVE no grant` and a job's `--wait` bounds nothing. A request under a turn passes through. The log reads `turn` when a token is dealt and `released`, with class `turn`, when it goes back, each naming its run's grant as `run`. A turn goes back when its job ends, and at the next look of any request, a fifth of a second apart, when its holder or its run's holder is gone; its time then counts to its run's. A job whose turn went back while it ran, its run gone, is stopped as a grant past its bound is: SIGTERM, then SIGKILL to its tree 10 s later.
- **A turn's compiles (#3221).** A job's `throttle.mjs` gives its command a jobserver of the job's own, GNU make's named pipe through `CARGO_MAKEFLAGS`, which starts empty: cargo runs its first compile on no token, which is the turn's. Each second it lends the pipe the pool's free tokens up to an even share, the pool over the turns held less the turn's own, and takes back what the pipe holds unread while any job waits for a turn. So the machine never compiles more at once than the pool, whichever runs compile. A token a killed build held is lost to its job alone, and the pool has it back once the job ends.
- **Builds on the pool (#3549).** A `build` request from a chain that holds no grant, as `scripts/lease` and a lane command make, is admitted as a run is. The first build always starts; one more starts only while fewer than the ceiling are held, 4 on the Mac and 6 on the Spark, the owner's numbers, and the memory available, less a run's memory (8 GiB on the Mac, 24 GiB on the Spark) for each build grant still settling, leaves a run's memory for one more. It doesn't read the load, as a run's admission doesn't, and a request reads the machine only once it is first in line under the ceiling. Requests wait for admission in arrival order, for the caller's `--wait` or `--stall`, as before. An admitted build is a run of one job: its grant counts as a run's for turns, the same request then waits for a turn of the pool on its caller's bound (#3660): the deadline its `--wait` set when it asked, or its `--stall`, which starts again each time a turn of the pool is taken or given back, but never less than two seconds from its admission, the time tokens lent to other turns and left unread take to come back. With no turn in time it gives its admission back, starts nothing and reads as an admission timeout does. Its command gets a jobserver of its own through `CARGO_MAKEFLAGS`, lent from the pool as a job's is. A free token goes to the waiter whose run has had the least time on turns, so a new build goes before the jobs of a run that has had time. The log reads `granted` for the admission, then `turn`, and `released` with class `turn` when the token goes back, each naming the build's grant as `run`; the turn goes back with the grant, and the command's `DEEP_THROTTLE` names the build's grant. A build's own turn is no job's: a `build` or `test` request under the build's grant passes through at once with no turn, as before; a run asked there is admitted, nested, and its jobs take turns of their own while the build keeps its token; and `scripts/lease` inside an admitted run still takes no turn. A script that takes its build grant through `acquire()`, as `affected.mjs` does for its binaries and the preflight for its package build, is admitted and takes its turn the same way, but only a command `throttle.mjs` starts gets a pipe, so that script's cargo runs at its own job count on the one token. A pending timed request starts no new build and deals no turn, a held one holds every build outside its chain, and a window waits for every admitted build to end, as for runs (Drain). A held grant's bound (#2744) counts from the command's start, and a stall (#3334) bounds the wait for admission and then for the turn. A checkout older than this states 1 or 2 for the class, so its build requests are served only while fewer than that are held (#2902), and its builds take no turn. The log's `granted` and `timeout` entries for a top-level request of any class carry `waited`, the milliseconds since it asked.
- **Drain.** A timed request stops new top-level grants and new turns, nested or not, then waits for every holder outside its own chain, every turn among them, to finish or to have a descendant blocked in a throttle wait; a run whose jobs all wait for turns counts as waiting. A budget window (section 12a) waits for every grant to end, so it stops new grants but not turns: the runs admitted before it take turns until they end. A held timed grant holds every turn outside its chain. A bay-pair holder never counts as idle for a top-level timed request, and does for a nested one. Nested requests from current holders go before new top-level ones, so two chains that each hold a grant and each ask for timed both finish, in request order.
- **Measured runs.** `preflight.mjs` and `perf.mjs` claim timed before their timers start and hold it to the end, so a measured time contains no throttle wait. perf's lock is taken only under timed and accepts a lock held by an ancestor (`DEEP_PERF_LOCK=<pid>`, verified like `DEEP_THROTTLE`).
- **Tests that start a measured run.** A test that starts `perf.mjs` or `preflight.mjs` (or `tests/preflight.test.mjs`) from a copy of the whole `scripts/` folder, with the machine's own table, makes that request itself; inside an `affected.mjs` block it is nested under the block's test grant, and while it is pending no top-level grant on the machine starts, until the block's neighbours finish. Such a file is in `lanes.mjs`'s `timed` list, where the request passes through on the block's grant; `tests/takes-timed.test.mjs` finds them by reading the tree. A test with a HOME of its own has a table of its own (tables of a test's own, below), and a copy of `perf.mjs` with no `throttle.mjs` beside it takes no grant.
- **Tables of a test's own.** Only inside a test run, where the requester or an ancestor is `node --test` or vitest (read from the process table, not the environment), does a request use another table: `DEEP_THROTTLE_TABLE`'s folder when it is set, otherwise `$HOME/.deepbuild/throttle/`, whatever `DEEP_THROTTLE` names. `--test` counts only among node's own options, before its script, so a command line that carries the word further on is no test run. Outside a test run `HOME` is ignored, and a set `DEEP_THROTTLE_TABLE` is `BLOCKED throttle`, so nothing but a test leaves the machine's table. A test keeps its sandbox `HOME`'s table, as before; one that needs two `HOME`s on one table points `DEEP_THROTTLE_TABLE` at a folder of its own.
- **A hung holder's bound (#2744).** A CLI grant is held at most `--hold <min>`, 720 by default (the longest full run seen on the Spark was about 9 hours), while another request waits. Past the bound (a monotonic clock, so a Mac's sleep doesn't count), once a request from outside the holder's own process tree has been pending at two looks a second apart, `throttle.mjs` logs `expired`, sends its command SIGTERM, and when the command ends or 10 s pass, SIGKILLs each process of its tree as listed then, by PID and start; it releases the grant, prints `INCONCLUSIVE throttle: the <class> grant <id> was held past its <min> min bound while another request waited; its command was stopped`, and exits 3. A log that can't be written, or a `ps` that fails after the SIGTERM, doesn't stop this: the command itself is SIGKILLed when its tree can't be listed. While `ps` fails before that, the grant is looked at again each second; while the log can't be written, the release isn't recorded and the table reads `BLOCKED throttle` until it is repaired. Nothing ends a grant while no one waits, or one already given back. A budget window has no bound (section 12a), and `acquire()`'s callers hold timed for their own measured runs, with their own timeouts.
- **A stopped run stops its tree (#3433).** `runLanes` and `measureOnce` wait on their commands in `spawnSync`, so neither can answer a signal, and a kill of the run's process group misses a process in a group of its own (a bay's command, a test's detached fixture). So each process that runs them gets one watcher, `scripts/proof-stop.mjs`, in no group or tree of the run's. While a command runs, the watcher lists the process's tree by PID and start every half second, keeping a process whose parent died first, and leaving out what the process had running before the watch began and other watchers. A process started and orphaned inside one half second isn't seen. When the process dies with a command running (one dead but not yet reaped counts), or `measureOnce`'s capture stops at its timeout or buffer, the watcher stops that command's tree: SIGTERM to the processes in the run's own groups, 8 s for those in groups of their own to end (a run's cleanup, as `proof-runs.mjs`'s folder remover, ends once the run has), then SIGTERM, and SIGKILL 3 s later, to what is left; each look on the way adds what the tree started since, so a process given its time can't leave new ones behind. perf's `ETIMEDOUT` error, and so its `BLOCKED perf` line, names each process the stop ended as `pid <n> (<command>)`, or says the stop couldn't list them, never a count of 0 for a listing that failed. A lane whose process died gets its record written `INCONCLUSIVE` by the watcher, with its finished rows and a finding `stopped: the run (pid <n>) ended while its commands ran; the stop ended <k> processes: …`, unless a record of that lane and tree is already there, which stands. The lane is armed from its first command to its record, again with its rows after each command, so what runs between commands (cargo's listing) is stopped too. A command that ends by itself leaves the watcher nothing to stop, and it ends with its process. Every `ps` the watcher runs is bounded at 10 s, so one that hangs is a failed listing.
- **A window joins the line only when it is due (#3551).** `throttle.mjs window` is asked each hour, by the hourly schedule of section 12a, and decides by the table and by how long ago the last window closed, the newest `window-close` in the throttle's log. There are three cases. Empty: asked while the table holds no grant, 6 hours or more after the last window closed, it opens at once, as a top-level timed request with a measured run's 60-minute wait. Not yet: asked while a grant is held, less than 12 hours after the last window closed, or with none held, less than 6 hours after, it joins no line and stops no grant; it prints `INCONCLUSIVE window: <n> grants held; the last window closed <h> h ago` and exits 3, as a window with no grant does. Overdue: asked 12 hours or more after the last window closed, or with no `window-close` in the log, it stops new grants and waits for every held grant to end, with a wait of 720 minutes, a held grant's own bound (below). The two spans, 6 hours and 12 hours, are drafted. The count, like `waited` in the window's record, is of the table's grants by class, and a job's turn counts under its run's grant. A window asked while another is asked or open leaves as well, naming that window's pid, so the hours of a long drain line up no second window behind it. A log that can't be read is `BLOCKED throttle`, and a line of it that a full disk cut short names no close. `--wait <min>` sets the wait of a window that joins the line. On a test's own table (below) the two spans are `DEEP_WINDOW_APART_MIN` and `DEEP_WINDOW_OVERDUE_MIN`, in minutes, and one a test doesn't set is none, so a test that sets neither drains whatever is held, as its log is only as old as the test; the machine's table never reads them. The trust this gives up: none in what a window measures. A commit may wait longer for its window than if every drain were waited out, at most the 12 hours and the drain after them.
- **A stuck drain (#2744).** A timed request's wait bounds its drain. When it passes, the request leaves the table, so new grants start again, and its `INCONCLUSIVE no grant` line goes on with `; blocked by <class> grant <id> held by pid <pid> since <time> (<command>)` for each holder outside its chain that hadn't finished or waited; the log's `timeout` entry lists them as `blockers`. A top-level request that isn't a window marks its blockers in the table, unless a grant is marked already, so grants that started while drains were off are never marked; while a marked grant is held a pending timed request, other than a window, no longer stops new top-level grants: it still waits for every holder, so it can't drain until the marked one ends, by itself or by its bound. A hung holder therefore costs one slot for at most its bound, never the machine.
- **A full disk (#2869).** A failed write leaves the table as it was and takes its own file with it. A waiting request whose table write fails with `ENOSPC` keeps its place and tries again until its wait runs out, then reads `INCONCLUSIVE no grant`. When its last look's write fails, `acquire()` throws that `ENOSPC`, marked `waited`, instead of returning no grant: the request it couldn't take out of the table stays there until the caller's process ends. A request that can't join the table, and any other error, is `BLOCKED throttle`, as before.
- **The load, by who made it (#3067).** `node scripts/throttle.mjs load` is a reading, not a rule: it takes no grant, never takes the table's lock, writes nothing but its log, in a folder it makes when there is none, and stops no process; it runs until it is stopped by its PID. At its start and each minute after, it appends one sample, a JSON line, to `load.log` in the table's folder (`~/.deepbuild/throttle/load.log` on the machine; a test's own table keeps its own). A sample holds `at` (ISO time), `load` (the 1-minute load), `cores`, `grants`, `outside` and `top`. CPU is in cores, 1 being one core busy, from one `ps` listing of every process (`%cpu` over 100): what each used in the moment of the listing, not over the minute. `grants` has one entry for each grant in the table whose holder is running: `id`, `class`, `pid` (the holder's) and `cpu`, the sum over the holder and every process under it, with `compile` (commands named `rustc` or `cargo`), `node` (`node`) and `other`, which add up to `cpu`. A process under two grants, one nested in the other, counts once, in the outermost, and a holder of two grants under the one it took first, its other grant's entry reading 0. `outside` is every other process, the sampler's own among them, with the same four numbers. `top` lists the processes that used most, five at most and none that read 0: `pid`, `command` (the command's name, as `ps` prints `ucomm`: no arguments and no path) and `cpu`, and `grant`, the ID it was counted under, when it has one. When `ps` can't be run or the table can't be read, the sample is `at`, `load`, `cores` and `failed`, a short reason, with no `grants`, `outside` or `top`: a failed reading is never a zero. The log holds PIDs, grant IDs, classes and command names only. `node scripts/throttle.mjs load --report` reads the log and prints `<p>% of minutes above the cores (<n> of <m>)`, a sample counting as a minute and above when its `load` is over its `cores`; then, for the samples above that didn't fail, one line a class that held a grant and one for `outside`, each `<name> <p>%`, the mean CPU of that name as a share of the mean of all, to one decimal and adding up to 100.0; `outside`'s line goes on with its own three shares, `compile`, `node` and `other`. The shares are of the CPU read, which the cores bound, not of the load, so a line follows with the mean CPU read, the mean cores and the mean load of those samples, and one with the five commands under no grant that their `top` named most, by mean cores, when it named any. It names the count of failed samples and of lines it couldn't read, which count as no minute; with no sample above the cores it prints no shares, and with none of them read it says no CPU was read. It reads the whole log, so a reading of 24 hours starts from a log moved aside. A process is placed by its parents as `ps` lists them, so one whose parent has ended (a test's binary started through a shell that exits) reads as `outside`, and `compile` is the two names only: a linker or a build script is `other`. No cap, kill or refusal follows from a sample; the Linux machine's units aren't read.
- **GPU time and the line (#3240).** Every sample that didn't fail also holds `waiting`, `idle` and `busy`, and, on macOS, the GPU time by grant. `waiting` has a count for each of the four classes, `build`, `bay-pair`, `test` and `timed`, of the table's requests whose requester is running (by its `pid` and `start`, as a grant's holder): requests in line, never a grant held, and no job of an admitted run waiting for its turn (#3221), whose run already holds its grant. `idle` and `busy` are the cores not busy and busy, in cores, from the kernel's CPU times (`os.cpus()`) read when the sample starts and again once its listings are made, which wait a second; they add up to `cores`. The GPU is read once a sample, from one `ioreg` listing of each accelerator and its clients (`ioreg -r -l -d 2 -w 0 -c IOAccelerator`, run by name from the `PATH`, as `ps` is): each client names the process that opened it (the pid in its `IOUserClientCreator`) and the GPU time it has accumulated (the sum of its `AppUsage` entries' `accumulatedGPUTime`, in nanoseconds). A client's change since the read before, or its whole time when it is new since then, goes to its process (the first sample's read before is one the sampler makes as that sample starts, a second before its own, so every sample on macOS holds a read), and a process's GPU time to the grant its CPU goes to, by the same tree, or to `outside`: each `grants` entry and `outside` gain `gpu`, in seconds, and `gpuTop` lists the processes that used the most GPU time, five at most and none at 0, each with `pid`, `command`, `gpu` and `grant` as `top` has them. A process the listing names that `ps` didn't list counts in `outside` and in no `gpuTop`; one that ended since the read before takes its time since then with it. A sample with no GPU read holds `gpuUnread`, a short reason in this code's words, and no `gpu` or `gpuTop`, never a zero: an `ioreg` that can't be run, fails or lists no client, for this read or the read before it, and every sample on a machine other than macOS. The read after one that wasn't made gives the change since the last read made, so no GPU time counts twice. `load --report` goes on with `<p>% of minutes with a request waiting beside two or more idle cores (<n> of <m>)`, over the samples that hold `waiting`, a minute counting when its `waiting` sums to 1 or more and its `idle` is 2 or more, and prints no such line when no sample holds it. Then `GPU read in <n> of <m> samples, <s> s in all`, over every sample, above the cores or not; and, over those read, one line a class that held a grant in them and one for `outside`, each `GPU <name> <s> s, <p>%`, its share of the GPU time read, to one decimal and adding up to 100.0 as the CPU shares do, and `GPU top commands under no grant: <command> <s> s, ...`, the five commands `gpuTop` named under no grant with the most seconds in all. With no GPU time read it prints that first GPU line only. A sample whose GPU wasn't read counts in no share. Seconds are to three decimals. The sampler still takes no grant, stops no process and adds no cap.
- **Threads by grant (#3550).** The load counts the threads that run or wait for a core, which the CPU read doesn't show: one build held alone read a load of 66 on 18 cores with 5 idle. So every sample that didn't fail also reads the threads, on macOS. Once its process listing is made, the sampler makes one listing of every thread (`ps -A -M -o pid=,state=`, run by name from the `PATH`, as the process listing is): a line a thread, ending with its process's pid and the thread's state, and a thread is runnable when its state starts with `R`, running or waiting for a core. Each process the listing names goes where its CPU goes, by the same tree: to the outermost grant above it, or to `outside`, as one the process listing didn't name does. Each `grants` entry and `outside` gain `procs`, the processes the listing names under it, `threads`, their threads, and `runnable`, those the listing shows runnable, so a process under two nested grants has its threads once, in the outermost. `runTop` lists the commands with the most runnable threads, five at most and none at 0: `command`, the name as `top` has it, `runnable`, the runnable threads of every process of that name counted under one grant, or of every one under none, and `grant`, that grant's ID, when it has one. So a name under two grants, or under one and under none, has an entry for each, and a process the process listing didn't name is in none. A sample whose thread listing couldn't be made holds `threadsUnread`, a short reason in this code's words, and no `procs`, `threads`, `runnable` or `runTop`, never a zero: a `ps` that can't be run or fails, a listing that names no thread, and every sample on a machine other than macOS. `load --report` goes on with `threads read in <n> of <m> samples`, over every sample, and with none read it prints no more of these lines. Then, over the samples above the cores whose threads were read, one line a class that held a grant in them and one for `outside`, each `runnable <name> <t>, <p>%`: the mean runnable threads of that name over those samples, to two decimals, and its share of them all, to one decimal and adding up to 100.0 as the CPU shares do. Then, over every sample whose threads were read, above the cores or not, one line for each set of classes that held a grant in the minute: `held <what>: <n> of <m> minutes, <p>%, median load <l>, cores busy <b>, idle <i>, under grants <c>, runnable threads under grants <g>, outside <o>`. `<what>` is the classes held, in the order `build`, `bay-pair`, `test`, `timed` and joined by ` and `, as `build and test`, or `nothing`; `<m>` is the count of those samples and `<p>` the line's share of them, to one decimal and adding up to 100.0; the load is the median, the mean of the middle two of an even count; `<b>` and `<i>` are the means of `busy` and `idle`, `<c>` the mean CPU read under the minute's grants, and `<g>` and `<o>` the mean runnable threads under them and under `outside`; all six are to two decimals. The lines come with the most minutes first, and among equals in the order the log first holds them. Last, `top commands under no grant, mean runnable threads: <command> <t>, ...`: the five commands `runTop` named under no grant with the most runnable threads, each as a mean over the samples above the cores whose threads were read, when it named any. A sample whose threads weren't read counts in no line but the first. The log still holds PIDs, grant IDs, classes and command names only; the sampler's own cost with the listing stays under 1% of one core, and it still takes no grant, stops no process and adds no cap.
- **A wait bounded by a stall (#3334).** With `--stall <min>` (`acquire(class, { stall })`) in place of `--wait`, a request has no fixed deadline: it keeps its place in line for as long as grants of its class change hands, the bound starting again at each look that finds a grant of the class taken or given back since the last. Once none has for `<min>` minutes the request leaves the line, prints `INCONCLUSIVE no grant: no <class> grant changed hands within <min> min`, going on with `; blocked by <class> grant <id> held by pid <pid> since <time> (<command>)` for each holder of its class, and of timed, outside its chain, logs `timeout` with those `blockers`, and exits 3; its `granted` and `timeout` entries carry `stall` in place of `wait`. It marks no holder, as only a drain does. An open budget window stops the bound running down, as it does a wait. A request gives `--wait` or `--stall`, never both.
- **#1015.** Once `deep lease` runs in this repository, a timed drain also waits on `deep lease` holders on the machine. Until then #1015 leaves commands under this script alone, so the two never meet.

Each caller waits for its grant at most:

| Caller | Grant wait |
|---|---|
| A lane command, and a cargo test's `-- --list` | 30 min |
| timed inside a `proof-runs.mjs` spawn | 15 min |
| A measured run's top-level timed | 60 min |
| A budget window (section 12a, #3551) | 60 min when it opens on an empty table; 720 min when it is overdue |
| An `affected.mjs` run, once for its binaries' build grant and once for its test grant | 30 min each |
| A job of an admitted run, for its turn | no limit |
| An admitted build, for its turn (#3549, #3660) | its caller's bound: what is left of its `--wait`, or its `--stall`, which starts again whenever a turn is taken or given back |
| A remote lane's far end, for its install and build grants and for each of its lane's commands and cargo listings (section 8, #3350) | while its class's grants change hands; out of line once none has for 30 min (`--stall 30`) |

An `affected.mjs` run queues once for its tests (#2574): first, on a build grant of its own when its tests need binaries, it claims its shards and builds those binaries in the worktree and in each (section 5, #2820), and holds the shards through its wait, its test-grant child naming itself in their locks once it starts; then it asks `throttle.mjs test --wait 30` as its admission (#3221) and runs as that grant's command, so every job of the run, the package build (whose outputs it then clones into the shards), `cargo test`, clippy, the lints that ask, the vitest and `node --test` blocks and the alone groups, with shards or without, passes through on it and takes its turn on the machine's pool. It gives the grant back when its last untimed job ends; its timed blocks then each ask for their own timed grant. So at most as many runs as the ceiling are admitted at once, their jobs taking turns, and the rest wait for admission in arrival order with nothing started; a run started under a caller's build or test grant is admitted at once with no slot of its own, and its jobs take turns as any run's; one started inside a job, as a test that runs `affected.mjs` itself, passes through on that job's turn; and their timed blocks ask as the caller would. With no grant in the wait the run prints `INCONCLUSIVE no grant`, an `INCONCLUSIVE` line naming each file it would have run and its `INCONCLUSIVE affected:` summary, and exits 2; when the throttle's table can't be used, the same lines read `BLOCKED`, and it exits 3. Stopped by its PID (SIGTERM or SIGHUP), the run passes the stop to its jobs, starts no more, and gives the grant back only once they have ended and it has released its shards; it then prints `BLOCKED affected: stopped by <signal>` and exits 128 plus the signal. A stop while the run waits for its build grant ends it at once; one during the binary builds is seen once the builds in the checkout under way have all ended, which for cold builds can take hours, and the run then gives back its shards and build grant, prints `BLOCKED affected: stopped by <signal> before its test grant` and exits 128 plus the signal, having taken no test grant; one in the moment before the run sets up its stop, or one that makes a build fail, ends the run BLOCKED or 128 plus the signal without that line.

A test job that stands still is stopped (#2627). A test that starves its worker's event loop defeats vitest's own limit (#2783), and a handle a test leaks keeps its file from exiting (#2804), either for ever. So once a vitest or `node --test` job's log and report have both stayed the same for 360 minutes, above the longest stretch a test may write nothing (`tests/acceptance/1781`'s 120-minute build hook runs before its 120-minute tests with nothing written between, and the timed lane's limits reach 240 minutes, in `tests/acceptance/416` and `140`), `affected.mjs` sends the job SIGTERM and 10 s later SIGKILLs each process of its tree, by PID and start, as #2744's bound does; the job's throttle then ends by itself and gives back its grant, or is SIGKILLed 5 s later. The job ends once they have, and reads by what it reported before the stop: those results stand, each of its files with no result reads `INCONCLUSIVE` naming the bound, and so does the job itself, since the file it stopped in may be part run; the run reads INCONCLUSIVE, goes on with its other jobs, and gives its grant back as usual. A job still waiting for its turn has started nothing, so its wait is never standing still: its 360 minutes count from its turn. `DEEP_JOB_IDLE_MIN` sets the bound in minutes, for tests.

On a timeout the first line is `INCONCLUSIVE no grant` and the exit is non-zero. A wait never eats into a run's own timeout: in the before and trace lanes the timed set spawns only after its grant, so after a 14-minute wait it still has its full 20-minute `TIMEOUT`.

The trust turns give up (#3221): none in what a test proves, since a job still runs alone in its shard and a turn is only a wait before it starts. A run's time now depends on the runs beside it, as it already did through the load. An admitted run holds its shards and their disk while its jobs wait their turns. A vitest block holds one token whatever its workers use, so the pool bounds jobs and compiles, not every core a job's tests keep busy.

The trust builds on the pool give up (#3549): none in what a build produces, since each cargo still builds in its own checkout's `target/` and cargo's own lock keeps two builds of one folder apart. A build's time now depends on the builds and runs beside it, as a run's does. Several builds hold memory at once, which the memory rule admits them by. A build that starts a run holds its token while that run's jobs take theirs.

`throttle.mjs` and `perf.mjs` join the guard's list of the proof lanes' own code, so a change to either needs a signed approval tag.

### 6a. Merge trains for the affected suite (#3018)

Each PR's own `affected.mjs` run builds its own test copies, about 45 GiB on the Mac, and holds a test grant for hours. A train is one `affected.mjs` run over several PRs that have each passed their proof lanes. The proof lanes stay one issue per change; a train is about the affected suite only.

`node scripts/train.mjs <pr>@<sha> ... [--wide] [--timed] [--slow]` runs in a checkout with no uncommitted change to a tracked file. A test that starts a package's build reads whatever `dist` the checkout holds, and `affected.mjs` rebuilds only for a change under `packages/*/src`, so a train runs in a fresh clone of main, as every Mac run does, not in a worktree that has built another branch. Each PR is named by its number and pinned to its head, as a full commit SHA, in the order they are to merge.

- **What it reads.** One `git fetch` from `origin` of `refs/heads/main` and each PR's `refs/pull/<n>/head`. The main commit is `origin`'s `refs/heads/main` at that fetch. A PR whose head there isn't the SHA it is pinned to stops the train: `BLOCKED train: #<n>'s head is <sha>, not <the pinned sha>`.
- **The train branch.** The PRs are merged in the order given onto the main commit, each merge made in git's object store, before any file of the checkout changes. A PR that doesn't merge stops the train before anything is checked out, built or run: `BLOCKED train: #<n> doesn't merge after <what was merged before it>: conflict in <paths>`, exit 3, with no record; a `git merge-tree` that fails for another reason names no PR (`BLOCKED train: git merge-tree failed: ...`). A train that merges is checked out as the temporary branch `train/<the first 12 characters of the train tree>`. When the run ends, however it ends, a stop too, the checkout goes back to where it was and the branch is deleted; a checkout that isn't back on its branch or commit, clean, with the branch gone, prints `BLOCKED train: the checkout didn't go back ...` and the train exits 3 whatever its record says. Nothing is pushed.
- **One run.** The train starts `node scripts/affected.mjs` once, on the train branch, with every path the train tree changes from the main commit, and passes on `--wide`, `--timed` and `--slow`. Its results count only when its exit status is the one their state maps to; otherwise the run reads as one that wrote none. That run selects the union of what the PRs change, builds once and takes its one `test` grant (section 6); the train takes none of its own. A train that changes no path from main stops `BLOCKED train` before anything is checked out, since `affected.mjs` with no path reads the change from the checkout instead.
- **Each file's result.** `affected.mjs --results=<file>` writes, when the run reaches its last line, `{ "state": <the last line's state>, "files": [{ "file", "state" }] }`: one entry for each test file it selected and each crate, as `cargo test -p <name>`, the unrun ones too. A file's state is `FAIL` when a new failure names it, else the worst `BLOCKED`, `INVALID` or `INCONCLUSIVE` among its tests' and skips' results, `INCONCLUSIVE` counting among them for a file of a job stopped for standing still or whose report was cut, which may be part run, and for every crate when `cargo test` failed outside any target, as a crate that doesn't compile, else `KNOWN` when its only failures are ones main already has, else `PASS` when a test of its passed, or for a crate when `cargo test` ran it, else `INCONCLUSIVE`: a file left to `--timed`, `--slow`, a person or a lane of its own, or one whose job reported nothing for it, never passes. `other` lists each new failure or unproven result that names no selected file, as the package build, a lint finding or a job, with its state. A run that ends before its last line, as with no grant, writes no file.
- **The record.** `~/.deepbuild/trains/<train tree>.json`, named by the run's `RECORD` line (a later train of the same tree, as the same PRs in another order, replaces it): `{ "main": <the main commit>, "prs": [{ "number", "head" }], "tree": <the train tree>, "state", "files": [{ "file", "state", "prs": [<number>] }], "other": [{ "id", "state", "prs" }], "host", "platform" }`. An `other` entry names every PR of the train. `state` and each file's are the run's; a run that wrote no results leaves `files` empty and `state` at `BLOCKED`, or `INCONCLUSIVE` when it exited 2. A file's `prs` are the PRs whose own changes select it: for each PR, `affected.mjs`'s selection over the paths its merge changed. So a failing file names the PR or PRs to drop, and dropping one and running the train again is the bisect step.
- **What it stands for.** `node scripts/train.mjs --read <record>` prints one line for each PR, and the run ends with the same lines. It reads `origin`'s `refs/heads/main` and each PR's head again (`git ls-remote`). `PASS #<n> <head>` only for a record whose state is `PASS`, or `NO NEW FAILURES #<n> <head>` for one whose state is that, while main is still the record's main commit and every PR of the train is still at its pinned head: the run tested the PRs together, so one PR's new head leaves none of them proven. Otherwise `INCONCLUSIVE #<n> <head>: main moved from <sha> to <sha>`, `: #<m>'s head moved from <sha> to <sha>`, or `: origin can't be read`, never PASS. In a train that wasn't green, a PR that a `FAIL` file names reads `FAIL #<n> <head>: <the files>`, and every other PR `INCONCLUSIVE #<n> <head>: the train read <state>`. `--read` exits 0 when every line is PASS or NO NEW FAILURES, 1 when one is FAIL, else 2; a record that names no PR or no files reads `INCONCLUSIVE train` and exits 2.
- **Merging.** Nothing merges by itself. The owner reads the record, then merges the PRs in train order, each pinned to its head (`gh pr merge <n> --match-head-commit <sha>`). Main moves with the first merge, so the record is read before it, not between merges.

## 7. The `alone` block, split by reason

The `alone` block in `lanes.mjs` exists for three different reasons, and each gets its own treatment:

| Why a folder is alone | Share | Where it goes |
|---|---|---|
| A sibling's cargo build rewrites `target/debug/<bin>` under it | Up to 29 of 85 folders | The parallel block, reading its binary from `DEEP_BIN_DIR` (section 5) |
| A load or timing gate | 56 folders | The timed list (T9a), run only under a timed grant |
| A resource it shares, such as #236's shared sandbox log stream | Any folder sharing one, whatever its other reasons | Stays alone |

A folder moves only when its sole reason is the binary rewrite, and only after its wrong program fails in the parallel block, before it leaves `alone`. Roughly 70–80 acceptance files spawn `cargo` themselves. An acceptance test is never edited by the agent fixing the tooling, so each needs a blind redraft (AGENTS.md, Proof) before it can read `DEEP_BIN_DIR`. Those are separate small blind jobs; T4 lands the mechanism and moves only the folders whose files need no redraft or whose redraft has merged. For #1123, the owner subsequently requested one PR: independently drafted redrafts may instead land as separately reviewable adoption commits before the scheduling commit within #2321. This packaging exception retains the approval guard and every moved file's wrong-program-before-removal proof; it waives no acceptance criterion. On 2026-11-12 the owner also made Spark optional for #1123: its required proof is on the Mac, with any Spark or Linux run supplemental and labelled by its actual platform. This host exception changes no acceptance threshold or required Mac reading. On 2026-11-13 the owner moved two lines of #1123 from its acceptance criteria to its Proof, word for word: that the parallel block absorbs the folders, each moved file's wrong program failing there before it leaves `alone`, and that the alone block's wall time before and after is a reading. Saved output proves both, the reading taken on the folders that move through the unit lane's own two blocks on one commit; the trace lane reads the two criteria that remain, each with its tagged test.

**A reason per entry (#3066).** `lanes.mjs`'s `aloneReasons` names one of the three for an `alone` entry: `binary`, `timing`, or `shared: <resource>`. Each was read from the entry's files, its comment in `lanes.mjs`, its suite's README or the commit that listed it, and an entry none of them settles has no reason until the owner names one; where several hold, shared outranks timing and timing outranks binary, so `binary` counts the entries a redraft alone could move. `node scripts/lanes.mjs alone --by-reason` prints the count per reason. `scripts/alone-lint.mjs`, in the lint lane, fails an entry with no reason or a fourth one, an entry of the merge base that left `alone` with any reason but `binary`, and a `binary` one that left while a test file of its, or a helper it imports, still reads `target/debug` or `target/release`, starts `cargo` or starts a hub; an `affected.mjs` run prints each as a `NEW FAIL`, naming the entry. A new suite's own lane file names its reason as the first words of its `why` (`"why": "shared: the GPU; each file draws on Metal"`).

**A suite's own lane file (#1327, #3419).** A new suite that must run alone says so in its own folder, `tests/acceptance/<issue>/lane.json`, as `{ "alone": true, "why": "<reason>" }`, and `lanes.mjs` adds the folder to `alone`. So does a new redraft or oracle folder, `tests/acceptance/<issue>-<suffix>/lane.json` whose suffix holds `redraft` or `oracle`, and a new such subfolder of a suite, landed or not. The file may also name files of its own folder as timed and as slow, `{ "alone": true, "why": "<reason>", "timed": ["budgets.test.ts"], "slow": ["build.test.ts"] }`, and `lanes.mjs` adds them to `timed` and `slow`. Running alone loses nothing, and an unrun timed or slow file reads INCONCLUSIVE, never PASS, so the file lands with its folder's files and needs no signed approval. It can't take a test out of a lane, skip one or mark one by hand: those stay in `lanes.mjs`, under a signed approval, as does every entry for a folder that has landed. The guard refuses, even with an approval, a lane file the change adds or edits in any other shape, one whose `timed` or `slow` names a file outside its folder, one the change's tree doesn't hold or one that an earlier commit than the lane file's added, in any folder, and any other name a disk that folds case reads as one of those paths. Unless approved, it refuses a new one anywhere else under `tests/acceptance/`, where `lanes.mjs` reads none; one in a numbered folder of another issue than the one the change names; one in a folder whose files landed before it; and the change or removal of one landed on main, as for a test. A redraft folder's lane file may come with any issue's change, since a redraft is often another issue's work. `lanes.mjs` runs the folder alone while the disk holds the file, whatever it holds, so nothing in the file can loosen a run; its `timed` and `slow` lists count only in the one shape the guard lets land. The lint lane (`alone-lint.mjs`) fails a new `alone`, `timed` or `slow` entry in the lane lists for a folder or file the change adds, and its Fix line names that folder's `lane.json`. The entries already in `lanes.mjs` stay there, and `231-oracle/`'s lane file, which landed when `lanes.mjs` read none there, stays unread until an approved edit says otherwise.

### 7a. Shards, exclusive folders and slow files in `affected.mjs` (owner decision, 2026-11-07)

Measured over the last 80 merged PRs on 2026-11-07, `affected.mjs` took about 3.3 hours a PR on the Mac, at the fastest run recorded for each file. Three quarters of that was the `alone` block: a median PR selects 389 of its 1,047 files, run one at a time. The owner decided, to bring the average PR under 10 minutes, that until T4 and the blind redrafts land:

- **Shards.** The alone block's folders run side by side, each in a shard: a fixed-path workspace, `~/deepbuild-shards/<k>/`, holding the worktree's exact tree written in place by the bays' rule (section 4), its own `target/` kept across runs, and the worktree's `node_modules/` and package builds cloned copy-on-write each use (macOS's `cp -c`; elsewhere GNU `cp --reflink=auto`, which copies where the disk can't clone, as on ext4). On macOS a new shard starts from a clone of the worktree's files, `target/` with them; elsewhere git writes its tree alone and it builds its own `target/`, since a copy would be many GB a shard. On macOS too, a folder that is or holds another worktree of the repository, as the main checkout's `.claude/worktrees/` does, stays behind. A folder still runs one file at a time, and only in one shard at once, so its files and its builds never meet another's: a sibling's cargo build rewrites `target/debug/<bin>` only in the shard it runs in. The shards run beside the parallel block, on the run's one test grant (section 6), and `DEEP_SHARDS` sets how many, half the cores by default. A shard is taken, new or reused, only while the disk holds 5 GB for it above #1017's 30 GB floor, since its tests' builds grow it; with none, the block runs in the worktree as before. A new shard's first builds compile the workspace crates its tests build at its own path: deep-hook and deep-show took 2.4 minutes and 3.4 GB, the whole workspace about 3.5 minutes and 6 GB. A shard leaves when a run that claims shards finds that no live process holds it and that it was last made a tree more than three days before: the run takes the shard's lock, removes the shard and then the lock, highest number first, and prints one line, the shards removed and the bytes `du` gave for them (#3547). When it was last made a tree is the time of its `.git/packed-refs`, which each use writes, and three days is hygiene's figure for an idle `target/` (section 9). Each use names the worktree's objects in the shard's `alternates` when they aren't there yet, keeping the lines other repositories wrote, so a shard one clone made serves another whose HEAD and tree live only in its own objects (#3515). A run asked for shards that claims none says so on stderr as it claims, apart from the `SHARD` lines on its stdout; a lane, which logs both into one file it reads at the end, still shows it only then.
- **Compiles at once (#2741, #3221).** Cargo starts a compile per core, and the shards' builds pass through on the run's test grant, so on 2026-11-16 one run's shards and worktree built seven at once with 95 `rustc` on 18 cores. Once the test binaries are built, one at a time, each job of the run, in a shard or in the worktree, takes a turn on the machine's pool of job tokens, a core less one, which every admitted run's jobs share (section 6), in place of a jobserver of the run's own. Every cargo a job starts runs its first compile on the job's turn and the rest on the tokens its job's pipe lends it from the pool. Cargo builds one at a time in a folder's `target/`, so the runs on a machine never compile more at once than the pool, and a run takes at most the cores less one shards, whatever `DEEP_SHARDS` says. The timed blocks compile without the pool. A cargo killed while it holds lent tokens never gives them back (#2848): its job lends that many fewer until it ends, when the pool has them back, so a later job's build gets its share again and the run has no loss to report. A run that a test starts with a table of its own takes turns on that table's pool.
- **Wide suites.** A test that starts a package's build, as `packages/cli/dist/main.js`, is selected by a change in that package, or by any change in its own package's folder; one that reaches the change only through another package is wide: listed on the `WIDE` line and run by `--wide`, the main watch (#1333) and the release preflight, and the run reads INCONCLUSIVE (owner decision on #2574, 2026-11-15). A one-line hub change selected 1,205 test files through the CLI before.
- **Settled suites (#3064, owner decision 2026-11-21; widened by #3593, owner decision 2026-11-26).** Acceptance suites reach the product through its binaries and the CLI, so a one-line change to `crates/deep-hook/src/main.rs` selected 1,176 untimed test files, and the main watch (section 12b) runs the same suites again after the landing. A suite is a folder `tests/acceptance/<issue>/`, named by its issue's number alone. One on the watch's settled list (section 12b), holding on disk the same files the list names for it, is left to the watch however the change reaches it: by import, near or far, or through a process the suite starts, a Rust binary or a package's build such as `packages/cli/dist/main.js`. Until #3593 only process reach left a suite, and most suites of closed issues import the changed package, so a full list left at most 23% of their files. The run prints one line, `SETTLED <n> …`, with the count of suites left and each one's folder, on `--list` too, and reads INCONCLUSIVE, as for WIDE. Three changes run the suite whatever the list says: one whose commit messages name the suite's issue (`Closes #n`, `Part of #n`, by the pattern the trace lane reads them with; when the commits can't be read, no suite is left), one that adds or edits a file under the suite's folder, and one to a file a test of the folder or its helper reads by path, in a crate or anywhere else: the changed file itself, or a folder holding it, named as a path the same file doesn't also import as a string literal (a literal `import('…')` is import reach; a computed one counts as a read), or the changed file spelled in a string of its own as a path from the checkout's root, as `'docs/technical-design.md'` or `'./scripts/lanes.mjs'`, in a test of the folder or a file under the test paths it imports. Such a spelling keeps the suite even where the string goes to a process it starts, so the rule errs toward running. A path the suite builds from parts, as `join(root, 'scripts', 'lanes.mjs')` or `` `${root}/docs/x.md` ``, isn't seen. A change in a package whose files a test of the suite imports itself no longer runs it (#3064's own-package case): that is the import reach #3593 leaves to the watch. The changed package's own tests outside `tests/acceptance/` are no suite and still run. The trust given up: a regression in a closed issue's behavior that a change reaches by import, as by a process, is found after the landing, by the watch's next run, at most 5 landings or 6 hours later, and nothing unrun reads PASS. A package's folder or its build named by path, as `packages/hub/` or a file under its `dist/`, counts as started, whatever the test does with it. `--settled` runs the settled suites too, as `--wide` runs the wide ones, and the run then reads no list. The list is read once, before the run waits for its test grant. With no list at `~/.deepbuild/main-watch/settled.json` (the `HOME` the run was given), or one it can't read as the list of section 12b, nothing is settled: the run selects as it did before this rule and says so on one line, `SETTLED no list: …`, naming the file and why. The main watch and the release preflight run every suite.
- **Exclusive folders.** The folders whose reason is the machine itself, `lanes.mjs`'s `exclusive` list (#16's and #315's socket timing, #236's sandbox log stream), run after the shards, one at a time, in the worktree, with nothing beside them.
- **Slow files.** `lanes.mjs`'s `slow` list names the files whose fastest recorded run took over two minutes. `affected.mjs` leaves them, as it leaves the timed ones, unless `--slow` or the change adds or edits the file, and an unrun slow file makes the run INCONCLUSIVE, never PASS (invariant 2). The release preflight runs them all. The budget window runs none: it runs only the tasks of `benchmarks/budgets.json` (section 12a), so a budget criterion that only a slow or timed test judges is never the window's to prove, and its record lists it as unmeasured.
- **The hour (#3567, owner decision 2026-11-26).** An `affected.mjs` run ends within 60 minutes of its start, its waits for a grant included. At the bound it starts nothing more, stops each job still running with its process tree, gives back its grants and reads INCONCLUSIVE, naming each file that didn't finish and each that never started; a FAIL read before the bound stays a FAIL. A run still waiting for its first grant then ends INCONCLUSIVE, naming the class. A rebuild before a job of what a cleanup removed (section 7b) is work started, so at the bound there is none; before a timed job, the run's own grant given back, it waits for a build grant of its own, for admission and then for its turn of the pool (section 6, #3549, #3660), at most the lesser of 30 minutes and the time left to the bound; with no turn by then it builds nothing and the run reaches its bound, and a build that runs into the bound starts no job after it (#3588). A file whose tests ran over 10 minutes is named on one `SLOW` line with its minutes, for the `slow` list. The release preflight has no bound.
- **The preflight's alone block (#3137, owner decision 2026-11-22).** The preflight's unit lane (`scripts/preflight`, local and release alike, through `runLanes` in `lanes.mjs`) runs its alone block as `affected.mjs` runs it, through that script's own entry. The lane still names the block as one serial vitest command, `aloneCommand`, whose listing is the block's files, and `runLanes` runs it as `node scripts/affected.mjs --alone --slow --timed`, which takes the files that command lists, whatever the change, and runs nothing else, no lint and no other block. Its folders run side by side in shards on the run's one jobserver, as above, then the exclusive folders one at a time in the worktree, then the timed files one at a time under a timed grant, which the preflight's own passes through; the slow files run with the rest, so the preflight still runs every file whole. Every file of the block that calls a timing helper is on the timed list, so none runs beside a shard. The parallel block, cargo test and `node --test` run before and after it as they did. The run writes each test's result into its `--results` file, and `runLanes` reads that as it reads a runner's report, so the unit lane's record holds every test as before. On 2026-11-22 the block held 3,343 files, 249 of them timed. The main watch (section 12b) runs the same unit lane, so its alone block runs in shards too, and its timed files ask for a timed grant nested in the lane's build grant.
- **Recorded reach, a reading (#3065).** The selection goes by what a test's sources name, an upper bound: a helper that names `debug/deep-hook` selects every test that imports it, whether or not the test starts the binary. `node scripts/reach.mjs record` measures the gap. It runs the unit lane's test files, or those it is given, each in a job of its own on one test grant, and writes `~/.deepbuild/reach/<tree>.json`: for each file, the workspace binaries its processes started (from `DEEP_BIN_DIR`, or by any path when a node process starts them), whether one started cargo, and the repository source files its node processes loaded, from `NODE_V8_COVERAGE`'s file list. The record holds paths and names only. A file that didn't run whole and pass has no row, nor has one whose node process left no coverage, killed or still running at its end. A row can't show, and so reads as not reaching: a binary another program starts by a path of its own, or under another name; a crate that is loaded, not started; a file a test reads without running it; code that runs outside node; what a node process loads once a program between it and the test cleaned or replaced its environment, in a worker thread given an environment of its own, or in a sandbox that can't write the job's folder; a script `vitest.config.ts` imports; and what a `node --test` runner loads itself, as its reporter. A test that started cargo counts as reaching every crate. `node scripts/reach.mjs compare <path ...>` prints, for a change, how many tests `affected.mjs` selects, how many the record shows reaching it and how many not reaching it; a test with no row counts as reaching, and so does every test when the changed file is neither code node runs nor a crate's, or feeds every suite, since no row can show a read of it. A crate's change reaches its binaries whole, and those of the crates built on it. It changes no selection: a record is one run's of one tree, to which a later recording of the same tree adds its rows, and the selection is every run's.

The trust a shard gives up is a bay's: it carries its `target/` from run to run, so its build is only as good as cargo's fingerprints. The trust turns give up here (#3221): none in what a test proves, since a folder still runs one file at a time in its one shard and a turn only delays a group's start; but an admitted run holds its shards, and the disk their builds need, while its groups wait their turns, so a run is admitted only while the disk holds that room above the floor. The trust a settled suite gives up: a regression in a closed issue's behavior that reaches its suite only through a binary or a package's build is found after its landing, by the watch's next run, at most 5 landings or 6 hours later, and the watch reverts that landing. Nothing unrun reads PASS. Lint scripts that build nothing run under no throttle grant, since in the build class they waited up to 30 minutes behind a neighbour's cargo build and ran nothing.

### 7b. A preflight that stops and resumes (#3296)

A full preflight can't finish in one sitting on a machine people use: on 2026-11-23 its alone block held 3,376 files, 251 of them timed, and 9 hours in 9 shards covered 1,405 of them, so the run was stopped and everything it had proven was lost, since its results file is written at its last line. Carrying results from other commits doesn't help: by today's selection 20 landings reach 99% of the block. A tree's own results are what a release proves, so they are kept.

**A job's results are kept as it ends.** The unit lane's jobs are the commands it starts with a report: the vitest parallel block, each group of the alone block (one turn's files), each timed file, `cargo test` and `node --test`. As a job ends, with its report whole (its `{"type":"end"}` row for vitest), an exit of its own, no unhandled error and no missing grant, the run appends one whole line to `~/.deepbuild/preflight/<tree>.jsonl` (mode 0600, in a folder of mode 0700): `{"key": {"tree", "host", "platform", "os", "node", "rust", "env"}, "job": "<its label>", "files": [<its files, none for cargo test>], "tests": [{"id", "state", "note", "skipped"}]}`. `<tree>` is `exactTree`'s, as every record names it, and a test's `state` is what its row reads before any list of known failures or skips is applied: `PASS`, `FAIL`, `BLOCKED`, `INVALID` or `INCONCLUSIVE`, with `skipped` on a test that never ran. A line that doesn't parse, or a job that was cut, killed or refused a grant, is no result.

**The key.** `host` is the machine's name, `platform` is `<process.platform>-<process.arch>`, `os` the operating-system build, `node` the Node version, `rust` the Rust compiler's version line and `env` a digest of the `DEEP_*` and `DEEPBUILD_*` variables the run was started with, keyed by a secret of the machine so it can't be turned back into values (some name agent binaries and keys). The variables the run sets for itself aren't part of it. A kept line counts only when every part of its key is the run's own; otherwise nothing it holds is used.

**What runs.** Only `scripts/preflight` keeps and reads results: the main watch and the proof lanes run everything as before. Each run lists the lane's files from the tree itself. A file with a kept result whose every row ran is not run again, and its rows are the run's. A file with none, or with a `BLOCKED` or `INCONCLUSIVE` row that no `skips` entry of `known-failures.json` covers, runs. An alone group runs only its files that must, and each timed file is a job of its own (below); the parallel block, `cargo test` and `node --test` run whole when any of theirs must. A `FAIL` or `INVALID` row ever kept under a key stands there: the file isn't run again and the lane doesn't pass, since re-running it until it passes is never proof. For any other state the last kept row of a test is its row. A kept line for a file the tree no longer lists is ignored. When a file has no kept result the lane reads `INCONCLUSIVE`, naming how many of how many are unrun, and never PASS (invariant 2).

**A stop.** A preflight told to stop (SIGTERM, SIGINT or SIGHUP sent to the process `scripts/preflight` becomes) stops its jobs and every process they started, vitest's workers and their builds among them, within 30 seconds, then exits with 128 plus the signal, its grants given back. What was kept stays. Before a job starts, the binaries the run's plan built are checked on disk, and a missing one is built again first.

**What it trusts.** A kept line is trusted as a lane record is: by the run that wrote it. It gives up nothing in what a result proves, only in how often a file is run.

**Filling and finishing.** One command does both, with no flag. `scripts/preflight` first fills the tree's kept results (#3296): it runs the unit lane alone, with no grant held by the preflight itself, so its untimed jobs wait and run as any session's do (an admitted run's on turns of the pool), and each timed file is a job of its own under one `timed` grant it takes and gives back. Once every file of the lane has a kept result whose rows all ran or that stands (#3296), the same command finishes: it takes the `timed` grant, times from the warm-up builds to the end of the checks, as it does today, reading the kept results in the unit lane in place of running them, then perf, the harness budgets and, at release, the release lanes. A run that can't fill, because a file has no result or an open one, ends before the finish, with exit 3 and a line `INCONCLUSIVE preflight: <n> of <m> test files have no result on this tree: …`, and reads nothing as passed. A checkout with no tree git can write keeps nothing and runs as before.

**What a kept line also says.** Its run and its time: `"run": "<id of the preflight that ran it>"` and `"ms": <the job's wall time>`.

**perf's base side.** perf's merge-base run reads the kept results of its own tree, by the same key, and passes `--kept` to its checks as the preflight does. Each side's unit record says how many test files it read from kept results, of how many, as `"kept": {"read", "of"}`. When one side read results and the other didn't, or they read different counts of them, perf's workload line reads INCONCLUSIVE and never PASS, since it compares unlike workloads.

**The budget** times the finishing run. The machine time the fill took is a reading, printed after `Checks elapsed` as `Kept: <jobs> jobs, <seconds> s of machine time, from <runs> runs`, its seconds being the sum of the kept jobs' `ms` and its runs the distinct `run` values, since it depends on the machine's load as any wall time does (section 10).

**Owner decision (answered on 2026-11-23: (a)).** The preflight's budget of 900 s bounds the finishing run, so the machine time of the fill is only the `Kept:` reading. Timing all of it, fill and finish, would have moved the budget to a day or more of machine time.

## 8. Remote lanes

`node scripts/lane-remote.mjs --host <host> <lane>` (T7) runs one of `lanes.mjs`'s check lanes, by its name, for a Mac session on another machine: `--host spark-ts` is the Spark. `<host>` is a name the machine's `ssh` knows.

- **Ship the exact tree.** A `git push` of the commit, a bundle of the uncommitted changes (the bytes of `git diff --binary HEAD`) and a tarball of the untracked non-ignored files, plus the merge base of `HEAD` and `origin/main` computed on the Mac. With them goes the shipment's manifest, one JSON object: `commit`, `base` (the merge base), `tree` (the tree hash of what is on disk, as every record names it), `bundle` and `untracked` (the SHA-256 of the bundle's bytes and of the tarball's) and `from` (the sending machine's name).
- **One Spark worktree per session**, `~/deepbuild/.claude/worktrees/<name>`, never relocated during its life, where `<name>` is the sending machine's name, the Mac worktree's folder name and a hash of its path. It is a repository of its own that borrows the objects of the machine's clone, `~/deepbuild`, when there is one: a ref it sets is its own, so no other session's `origin/main` moves. It names the Mac checkout's `origin` as its own and never fetches from it. Each shipment replaces its files with the shipped commit's, applies the bundle and unpacks the tarball, each file dated as it lands, so a kept build sees it as new; what git ignores there (`target/`, `node_modules/`, the packages' builds) stays from run to run. One lane runs there at a time: while the far end of an earlier shipment is still running, by its PID, a new one changes nothing and reads `BLOCKED lane-remote`. Proof lanes run from there into a Spark bay pair, under the Spark's throttle, as every lane command does.
- **The far end checks what it was sent.** The same script, started in that worktree with the lane's name and no `--host`, is the far end: `node scripts/lane-remote.mjs <lane>` reads the manifest from its standard input. It sets the worktree's `refs/remotes/origin/main` to the shipped merge base, computes the merge base of `HEAD` and that ref itself, and when the two differ it runs nothing, writes no record, prints `BLOCKED lane-remote: the merge base shipped is <shipped>; <host> computes <computed>` and exits 3. It does the same, naming both, when its `HEAD` isn't the manifest's `commit` or the tree on its disk isn't the manifest's `tree`: a shipped merge base and a shipped tree are verified, never trusted (invariant 1). Then it installs (`npm ci`, only when the lock's bytes changed since its last install there) and builds the packages, each under a `build` grant asked with `--stall 30` (section 6, #3334), so a deep queue that is being served keeps its place; `DEEP_LANE_REMOTE_STALL_MIN` sets that bound in minutes, for tests. When the throttle gives no grant, nothing more runs: the far end writes the lane's record of the tree with state `INCONCLUSIVE`, no rows, and one `INCONCLUSIVE` finding whose note is the throttle's `INCONCLUSIVE no grant` line, holders named, adds `bundle` and `recipe`, and ends `RECORD <path>`, so the near end reads `INCONCLUSIVE <lane> on <host>`, exit 2. An install or build that fails, or a throttle that reads `BLOCKED`, is `BLOCKED lane-remote`, exit 3, with no record. Then it runs the lane, whose commands and cargo listings ask their grants with the same `--stall` bound in place of `--wait 30` (#3350): a command the throttle gives no grant reads as any lane's missed wait does: an `INCONCLUSIVE` finding whose note is the throttle's reason, `no <class> grant changed hands within <min> min`, with the holders named for a cargo or plain command (a vitest job's report carries the reason alone), and a cargo listing that gets no grant leaves its tests unlisted, `BLOCKED` off the Mac. A lane run any other way keeps `--wait 30`.
- **The record comes back.** The lane writes its evidence record on the far machine as every lane does (T9b), and the far end adds `bundle`, the bundle's hash, and `recipe`, the manifest: the commit, the merge base, the bundle and the untracked tarball the tree was composed from, and who sent it. `host`, `platform` and `tree` are the far machine's own, as it read them. The far end's last line is `RECORD <path>`. The near end fetches that file and writes it into its own `~/.deepbuild/lanes/` as `<tree>-<lane>-<host>.json`, `<host>` being the record's own `host`, beside the record a run of the lane on the Mac writes. It prints `<STATE> <lane> on <host>` and `RECORD <its path>`, and exits 0 on PASS, 1 on FAIL, 2 on INCONCLUSIVE and 3 on BLOCKED or INVALID, by the fetched record's `state`, not by the far end's summary or exit status. A run that brings no record back whose `tree` is the shipped tree reads `BLOCKED lane-remote`, exit 3.
- **Merged per test.** A PR's unit verdict is the Spark run merged with a Mac `--only` run of the test IDs the Spark skipped, plus those that reach a platform-branching source: tests reaching `process.platform` sources, crates with `cfg(target_os)`, and platform-branching helpers. `node scripts/lane-remote.mjs --only <lane>`, on the Mac, on the same tree, reads the fetched record of that lane, then runs the lane's own test commands narrowed to those tests: the files of each row the far record marks `skipped`, the test files `affected.mjs`'s `select` reaches (wide ones too) from every tracked or untracked source that reads `process.platform` or names `target_os`, every test of the lane when one of those is a file every suite reads (`select`'s `every`, as a runner's setup), and `cargo test -p` for each crate it reaches from them or a skipped row names. It writes the Mac's record of the lane, `<tree>-<lane>.json`, with `only`, the files and crates it ran. A record of a whole run of the lane on this Mac and tree, one with no `only`, holds every such row already: it stands, and nothing runs. With no fetched record of the tree and lane it runs nothing: `BLOCKED lane-remote`, exit 3. So does a lane with no test command, as lint: nothing of it narrows, and a record of nothing run is no verdict. It ends with the merged line, `<STATE> <lane> (merged)`, and exits by that state as above.
- **How records merge.** `mergeRecords(tree)` in `lanes.mjs` reads every record of the tree and merges each lane's records, a Mac's (a `platform` starting `darwin`) and any other machine's, per test ID. A row that ran stands over a `skipped` row of the same ID, and among the rows that ran the worst state stands. Any FAIL wins: a Spark FAIL and a Mac pass of one test ID merge to FAIL. What a lane found outside any test, as a missing grant or a runner that died, is in its record as `findings`, each a state and a note, and counts whatever the rows merge to; so does a record's own state when neither its rows nor its findings explain it, and a state the lanes don't write reads INVALID. Within one record a skipped row and a row that ran of one ID stay as that lane read them. A lane whose records are all a Mac's reads as before any merge, by their own states. A lane with a record from another machine and none from a Mac is never PASS: what only the Mac can run is unrun, so it reads INCONCLUSIVE unless its record reads worse. The lint lane is the exception to merging: a lint record from another machine is a reading and is left out, whatever its state, so the lint verdict is the Mac's record alone, and INCONCLUSIVE without one. The tree's state is the worst of its lanes'. The merged verdict must equal a full Mac run of the same tree.
- **The Spark's copy-on-write folder (#3170).** `deep-hook`'s Linux staging test clones into `DEEP_TEST_COW_DIR`, which must make a reflink copy, and the Spark's disks are ext4. The folder is `~/deepbuild-cow`, the mount of a 4 GB sparse XFS image with reflink, `~/deepbuild-cow.img` (`mkfs.xfs -m reflink=1`, its root folder made the user's by a protofile), mounted at boot by an `/etc/fstab` line with `loop,nofail`. The variable comes from the `[env]` table of the Spark's `~/.cargo/config.toml`, so every `cargo test` whose `HOME` or `CARGO_HOME` is the user's gets it, in any lane, bay or shell; a variable set for a run still wins. A machine without the folder reads that test BLOCKED, naming the fix. On the Spark that BLOCKED names `~/deepbuild-cow` and means the image isn't mounted (the folder is then plain ext4): `sudo mount ~/deepbuild-cow`.

### 8a. The x86_64 lane (#1983)

No x86_64 machine exists, so `node scripts/lane-x86.mjs` on the reference Mac is the other CPU architecture for CPU checks:

- **The host.** A linux/amd64 container of the Rust toolchain image of `rust-toolchain.toml`'s channel, pinned by its index digest in `scripts/lane-x86.json`. The pin is the full image, not the slim one, because it carries `git`: cargo 1.99 runs `git gc --auto` before each git fetch and starts its git database over when that can't run, so without `git` the cache never holds two commits of one repository (gpui-shell's quickjs-jit and the workspace's) at once, and an offline build there, such as #2012's run of Rapier's own tests, fails. It never pulls: with no runtime, or no linux/amd64 image of the pin, its record is BLOCKED with one ask, naming `docker pull --platform linux/amd64 <image>@<digest>` for the image.
- **The record.** `~/.deepbuild/lanes/<tree>-x86_64.json`, #1115's fields plus `recording_machine` (the golden's machine), `lane_arch` (what the replay's own `deep-logic` reports), `host_arch`, `emulated`, `image_digest`, `network` (from the container's own interfaces), `bake_key`, Golden's `report` on FAIL and the `ask` on BLOCKED.
- **What counts.** logic.determinism `cross_machine` reads that record by tree and bake key: PASS only on a PASS record naming every field, on another architecture than the golden's and with no network; FAIL naming the step, item and field; BLOCKED with one ask without a record. A run on aarch64, natively or in a linux/arm64 container, reads `machines: same` and never passes. A reading taken in the lane is never a timing or a budget: logic.budget refuses each, naming the lane and `emulated: true`.
- **Merged as remote lanes merge.** `mergeRecords(tree)` in `lanes.mjs` takes the worst state of a tree's records and names the lanes holding it, so the lane's FAIL wins over the Mac's pass.
- **What emulation proves.** Our code compiled for x86_64 gives the same bits as the arm64 build; not real x86 hardware, and timings there mean nothing. A real x86_64 host that writes the same record with `emulated: false` replaces the container without changing any check that reads it.

## 11. Invariants

The four invariants of AGENTS.md, as the tooling keeps them:

1. **An agent's word is never evidence.** `DEEP_THROTTLE`, `DEEP_PERF_LOCK`, a bay's seal and a shipped merge base are each verified, never trusted. A remote lane's verdict is its evidence record, fetched back, not the Spark's summary line.
2. **Nothing missing or unrun passes.** A skip, a missing grant, a platform-absent test and a budget at a load above the cores are each INCONCLUSIVE or BLOCKED, never PASS, and a commit the budget window has not yet measured leaves its issue open. A Spark lint record is a reading. A merged unit verdict takes any FAIL.
3. **Agents can't change checks or decisions.** Each tooling script that decides a verdict joins the guard's list, so its change needs a signed approval tag. Agents never run or edit the budget window. Acceptance files are redrafted blind, never edited to read `DEEP_BIN_DIR`.
4. **A person sees only what needs a person, and never the same question twice.** The owner is asked the two questions of section 10a once, with the list that answers what they change. Large worktrees on open branches are listed for the owner, never deleted by an agent.

And for the machine: processes are stopped only by the PID that started them, never by name or port; no hooks go into a repo's settings; nothing runs on push or pull request.

### 12a. Budget windows (owner decision, 2026-11-02)

Agents run day and night, so no idle period exists for budgets, and a per-PR budget queue was the efficiency bottleneck. The owner decided on 2026-11-02 that budgets leave the PR's path but stay tied to each commit. [How we know version 0 works](technical-design.md#how-we-know-version-0-works) says so: each issue's budgets are measured on a reference Mac by a benchmark in the scheduled budget window, compared with the merge base, with the samples, margins and reference Macs it sets.

- **The window.** A few times a day `throttle.mjs` opens a budget window on each reference Mac: it stops granting build, test and bay pair, lets running grants finish, runs `scripts/budget-window.mjs`, then reopens. Agents keep thinking and editing; only their next build or test waits. `throttle.mjs window [--wait <min>]` is a top-level timed grant that takes no holder as waiting, so every slot empties, and a caller's grant wait doesn't run down while a window is pending or open. The throttle log marks it with `window-open` and `window-close`.
- **When it opens (#3551, owner decision 2026-11-25).** A window is asked each hour and opens when the machine is empty, and it waits a drain out only when it is overdue. The last window's close is the newest `window-close` in the throttle's log. There are three cases:
  - **Empty.** Asked while the table holds no grant, 6 hours (drafted) or more after the last window closed, it opens at once, with a measured run's 60-minute wait.
  - **Not yet.** Asked while a grant is held, less than 12 hours (drafted) after the last window closed, or with no grant held, less than 6 hours after, it joins no line and stops no grant. It prints `INCONCLUSIVE window: <n> grants held; the last window closed <h> h ago` and exits 3, as a window with no grant does.
  - **Overdue.** Asked 12 hours or more after the last window closed, or with no `window-close` in the log, it stops new grants and waits for every held grant to end, with a wait of 720 minutes, a held grant's own bound (section 6).

  A window asked while another is asked or open leaves too, naming that window's pid, and a log that can't be read is `BLOCKED throttle`. In a replay of the reference Mac's throttle log, 20 of 46 windows asked at four fixed hours with a 60-minute wait gave up after stopping new grants for an hour, and waiting every drain out opened each one at three times the stopped time; this rule kept the windows a day, and none gave up. The trust it gives up: none in what a window measures. A commit may wait longer for its window than if every drain were waited out, at most the 12 hours and the drain after them. A window stops no held grant: only a held grant's own bound ends it (section 6).
- **What starts it.** A schedule on each reference Mac that asks each hour, in a checkout of main that no session works in, such as this crontab line. It is installed by hand, and only there: a window elsewhere drains the machine for readings.

  ```
  0 * * * * zsh -lc 'cd ~/doneright && node scripts/throttle.mjs window' >> ~/.deepbuild/budget-window.log 2>&1
  ```

- **What it measures.** Every commit merged since the last window, each against its own merge base, 20 samples a side, with each issue's budget numbers unchanged. A commit merged during a window is measured in the next one. Merged means on the first-parent line of `origin/main`. A merge commit is measured by its branch tip against `git merge-base` of its parents, so a branch never answers for what landed on main beside it; a commit with one parent, against that parent. The window judges the tasks of `benchmarks/budgets.json` as perf does, and for each commit only those that reach a file the commit changed, by the selection `scripts/affected.mjs` makes for tests. A task the selection can't place, or marks wide, runs on every commit; one the commit can't reach isn't run, and the commit's record lists it as not reached, never PASS. The window has no cap on its length, since a commit longer than a cap would never be measured. A mark under `~/.deepbuild/budget-window/` says how far it got and moves only past a commit it recorded, so a window that dies loses nothing. The first window on a machine only sets the mark. Any record moves it: an INCONCLUSIVE commit isn't measured again, and its issue stays open with the reason on the record.
- **What it records.** One evidence record per commit, in T9b's record shape, with `commit` and `base` added, and `unmeasured`: the unticked criteria of the commit's issues that no task names. Each task of `benchmarks/budgets.json` names the criteria it proves, as `criteria`, a list of criterion IDs (`#<issue>.<h8>`, the trace lane's), and only a task's numbers are frozen once main has it, so naming one is no change to its budget. A pass closes that commit's issue only on criteria it measured: the issue has a `### Acceptance criteria` section, at least one line under it is unticked, and a task names each unticked line, so a `Part of #n` merge ticks the others. An unticked criterion no task names keeps the issue open and is named in the record as unmeasured, whatever its words: a budget only a timed test judges, or a line that says "in the local preflight" and is no budget. An issue with no such section, such as an umbrella, is never closed by the window. A miss leaves the issue open, naming the regression and the commit, and files a budget follow-up. A commit not yet measured leaves its issue open, never closed, so a pass leaves the issue open while a later commit of it waits in the same window. A load at or above the cores during a task makes that task INCONCLUSIVE.
- **Ticks (#1835).** The trace lane writes an evidence record of its own, `~/.deepbuild/lanes/<tree>-trace.json`, for the tree it ran on: a row for each criterion of the change's issue, PASS only for one a tagged test proved in that run. For each commit it takes, before it reads what the commit's issues leave unticked, the window ticks in each issue's body the unticked criteria that the record of the commit's change side holds as PASS, and names the record on a line of its own under each, so a criterion's line and its ID stay as written. Nothing else ticks: a criterion with no PASS row stays unticked, and so does every line when the window's machine holds no trace record of that tree.
- **Numbers and the table (#2674).** Each task's row keeps its numbers, so two commits compare and a climb can be drawn: `sides.change` and `sides.base` (null for a task the merge base lacks), each its p50, p95 and peak bytes over its 20 rounds and its instructions retired per round; `loads`, the one-minute load at each run's start and end, both sides' rounds then the limit runs; and `ms`, how long the task took. A load at or above the cores at any of them, or at the task's end, makes the task INCONCLUSIVE. Each window also leaves a record of its own beside its commits' records, `~/.deepbuild/lanes/budget-window-<start>.json`: its grant (the throttle log's `window-open` and `window-close` name it), `drain`, the milliseconds from its request to its grant, and `waited`, the grants it waited on, by class (#3551), start and end, the machine's fingerprint and cores, the load at its start and end, the commits it measured with their records, the tasks it ran, those it reached on no commit, and its longest task; a window over two hours (drafted) says so in its note, naming that task. On the reference Mac, `node scripts/budget-table.mjs collect` copies each window into `benchmarks/windows/<start>/` (`window.json`, a `<commit>.json` per commit, `throttle.log`), with home paths written `~` and hosts dropped, and rewrites `benchmarks/windows/numbers.md`: one line for each row of [Numbers version 0 has to hold](technical-design.md#numbers-version-0-has-to-hold), naming the tasks that measure it and its newest reading's date, machine, macOS build, load and method. A line is a result only from a window's records on a reference Mac, for the tasks whose own limit or target judges the row, none timing a debug build; anything else is a reading that says why, and a row no task judges whole is `unmeasured`, naming what is missing. The lint lane's `budget-table.mjs check` fails a line the records don't give and a record that reads PASS at a load at or above the cores or holds no numbers.
- **PRs.** A PR whose issue has reference-Mac budget criteria merges as `Part of #n` on its other criteria; the window proves the rest.
- **Who runs it.** Agents never run or edit the window. `budget-window.mjs` joins the guard's list, so a change to it needs a signed approval tag.
- **The preflight's budget (#3137, owner decision 2026-11-22).** `benchmarks/budgets.json`'s `preflight` budget is the preflight's own, never a window's task: `preflight.mjs` times the checks with their builds on its timed grant, from the warm-up builds to the end of `scripts/checks.mjs`, every lane of `lanes.mjs`'s `checks`, and perf, the harness budgets and the release lanes run after it, outside it. It moved once with its reason, as an estimate may (#12: 300 to 900 s on 2026-10-22), and moves again only as a task's ceiling rises (#2665): by an approved proposal, an `Approves: benchmarks/budgets.json › preflight › <limit> <before> → <after>` item for each limit it changes, whose entry records the measured full run it moves for as `measured`, `{date, machine, load, elapsedMs}`: the day, a reference Mac's model, a one-minute load below that Mac's cores, and the run's elapsed time, a run no earlier move recorded, with a `changeReason` of its own that names it. Nothing else of it changes. `validateBudgets` in `benchmark.mjs`, which perf and the window run, refuses a move with no approval, naming the item that would approve it, and an approved one with no such run.

**Reading rule.** An existing budget criterion that says "in the local preflight" is met by the scheduled budget window's record for its commit, once a task of `benchmarks/budgets.json` names it (#1874). On 2026-11-02, 258 open issues carried that phrase, 238 times in the criterion lines of 236 of them (not all of those are budgets; the rule reads only the budget ones), and several already have tagged tests, such as the budget tests under `tests/acceptance/104`, `159`, `331` and `365`. A criterion's ID is the hash of its normalized text, so rewording those lines would change their IDs and break the tags that prove them. Their text stays as written, and this rule reads it.

### 12b. Main is watched (#1333)

Nothing else runs after a merge, so `scripts/main-watch.mjs` does, on the run's host, in a checkout of main that no session works in:

```
0 * * * * zsh -lc 'cd ~/doneright && node scripts/main-watch.mjs tick' >> ~/.deepbuild/main-watch.log 2>&1
```

- **When.** A tick runs the unit and lint lanes of main's head, from that head's own `lanes.mjs`, once 5 landings reached main or 6 hours passed since its last run, and at every tick while landings are paused. A landing is a commit on main's first-parent line. Its lanes go through `runLanes`, so the throttle and `deep lease` hold them like any other. It calls no model and starts no hosted workflow.
- **A new failure** is one `known-failures.json` doesn't list. It runs again alone, up to three times. One that passes on a repeat reads INCONCLUSIVE and is filed once, with its runs, and nothing pauses. One that holds pauses landings and is bisected, running only that test, over the landings since the last clean run, which names the landing and its issue.
- **Recovery.** A pull request reverts that landing. It is merged once the failing test passes on it and nothing that passed on main fails there, and then the issue reopens naming the failure and landings open again. A revert that conflicts or doesn't clear main starts an attempt on the issue, a headless `claude` or `codex` run. Only once that attempt has ended with main still red is a person asked, once, by an issue titled `Ask: …`.
- **The gate.** `node scripts/main-watch.mjs status` prints `landings open` (exit 0) or `landings paused: …` (exit 1) from the job's state under `~/.deepbuild/main-watch/`, without fetching. The landing queue (#1331), and anyone landing by hand, reads it first.
- **The settled list (#3064).** After each run of the two lanes on main's head, the tick writes `~/.deepbuild/main-watch/settled.json`, whole and renamed into place: `{ "tree": "<the tree of the head it ran>", "suites": { "tests/acceptance/<issue>/": "<git's ID of that folder in that tree>" } }`. A suite, a folder `tests/acceptance/<issue>/` named by its issue's number alone, is on the list when its issue is closed as completed and the suite was clean in each of the watch's last 10 runs of main's head (drafted): every test file of the folder (`*.test.ts`, `.js` or `.mjs`) reported a test, every test those files reported read PASS, the lanes' records hold no row of the test runner's own that names no file (a report that ends before its run did, an unhandled error: each leaves every file's tests unknown), and the folder held the same files in all ten. A command whose report has a line that doesn't parse leaves no row at all, so no suite it ran is clean. A run in which one of its tests fails, is skipped or doesn't report, whatever a repeat alone says afterwards, and a change to the folder's files, each start the suite's count again, so a settled suite that fails is off the list that run writes and stays off until it has 10 clean runs again. A suite the unit lane doesn't run whole, as one with a `.test.mjs` file or a file `lanes.mjs` leaves to a person or to a lane of its own, is therefore never listed. The count is kept in the job's state, saved as the list is written. In a run where a suite has its 10, which issues are closed as completed is read with one `gh issue list --state closed --limit 100000 --json number,stateReason`, a `stateReason` of `COMPLETED`; when that fails the list is written with no suite, and the tick says so. A list that can't be worked out or written is removed and every count starts again, so nothing stays settled on an old one. `affected.mjs` leaves a listed suite to the watch (section 7a), which changes nothing in what the watch runs. The trust given up is section 7a's.
- **Listed failures lapse.** Each `failures` entry of `known-failures.json` ends `(#<issue>, added <YYYY-MM-DD>)`, and so does each `lint` key's value in `lintIssues` and each `timing` ID's in `timingIssues`. The lint lane's `scripts/known-failures-check.mjs` fails an entry that names no issue, names one that isn't open, or was added more than 14 days ago; a `lint` key naming a file the tree doesn't hold; a `skips` entry whose test the tree doesn't hold, by its file and its name; and a `skips` reason naming an opt-in variable its test's file never reads (#1873).
- **Listed failures end.** A test listed in `failures` or `timing` that passes in a tick's run, and a listed skip whose test ran to a PASS or a FAIL, fail the tick, naming the entry: the run isn't a clean one, and nothing pauses. In the tick's run of main's head, a FAIL on a `timing` ID is excused, as INCONCLUSIVE, only when the load (`DEEP_MAIN_WATCH_LOAD`, or the one-minute load average) is above the core count, as `classify` in `affected.mjs` reads it; at or below, it is a new failure, and the runs that follow it, alone, bisecting or on a revert, read it strictly (#1873).

## 13. Capacity

What each machine holds at once, with the throttle and the bays in place:

| | Mac | Spark |
|---|---|---|
| Resident sessions | At most 3, one of them proving | One worktree per remote session |
| build grants, a ceiling: each admitted build then takes a turn (#3549) | 4 | 6 |
| test grants, admitted `affected.mjs` runs among them | 2 | 6 |
| Job tokens, the turns every admitted run's jobs and every admitted build share | 17, a core less one | 19 |
| Bay pairs | 1, about 40 GB of disk | 3 |
| timed | 1, exclusive of everything; budgets count only in a budget window on a reference Mac | 1, exclusive of everything; its timings are readings |

A session waiting for a grant keeps thinking and editing; only its next build, test or proof waits. When the Mac's single bay pair is held, a second Mac session's proof waits for it or runs on the Spark by remote lane. The limits are the starting values T5 sets, and each test number is a ceiling (#2924): the first test grant always starts, and each one past it only while the 1-minute load is below the cores and the memory available, less 24 GiB for each test grant still settling (under 5 minutes old), still leaves 24 GiB for one more capped run (section 6). That is the Spark, whose runs are units capped at 24 GiB. The Mac reads the memory available from `kern.memorystatus_level`, and budgets 8 GiB a run in place of the 24 (#2980). An `affected.mjs` run's test grant is its admission, decided by the same rules without the load and only while the disk holds room for its shards above the floor; once admitted, its jobs take turns with every other admitted run's on the pool of job tokens, a token to the run whose jobs have had the least time so far, and never more of their jobs or compiles run at once than the pool (#3221, section 6). The trust this gives up: none in what a test proves, since a job still runs alone in its shard; a run's time depends on the runs beside it, as it already did through the load; and an admitted run holds its shards' disk while it waits its turn. The build number is a ceiling too (#3549): a build asked for under no grant is admitted as a run is, the first always and each one past it only while fewer than the ceiling are held and the memory available, less a run's for each build still settling, leaves a run's memory for one more, without the load. An admitted build then takes a turn on the same pool, a run of one job, and its compiles draw on the pool. The trust that gives up: none in what a build produces, since each cargo builds in its own checkout's `target/`; a build's time depends on the builds and runs beside it; and several builds hold memory at once, which the memory rule admits them by. A change to any of these is a change to `throttle.mjs` and needs a signed approval tag.
