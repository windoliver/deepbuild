# Checks

## What it is for

First-party check plug-ins that the hub loads as release packages, each registering a check kind through `deep.registerCheck`, so the core knows nothing of them and a requirement naming one is BLOCKED, naming the plug-in, while it is off. `playtest` (#184) is the check that requires live play: bots, a scripted input policy or a logic program, play seeded runs of a piece headless in replicas through `deep.canvas.play`; a run that gets stuck, misses a goal, traps or passes its step ceiling fails with its code, and every run's track replays without its bot to the same full-state hashes. From a save (#1047), `from: {save}`, every run and its replay start at the save's step once logic.layout has passed the save against the piece, and a save it refuses leaves the check with no run counted, INVALID. With a play interface `game.play@1` (#555), locked in the brief, its first-party bots (legal, explorer, descender) play a generated grid game through listed rows only, goals are expressions over the interface's names, each bot's `share` bands and `expect: miss` hold over its runs, a declared name the piece doesn't publish fails `play.missing` before any run, and a value outside its name's range fails `play.out_of_range`. #1048 adds two kinds beside it, `rules.legal` (each listed row is taken and each unlisted entry turned down, tested in throwaway copies of the states the named playtest's runs reached) and `logic.edges` (each listed control put at its kind's `control@1` edge values), a playtest's `soak`, a model bot whose runs count only through replay, and grids with layers and links. #556 adds `grid.reach`: its own breadth-first search, with key-and-door closure, over every floor the named playtest's runs generated (each run its own floors under `piece_seed: run`), a depth no run generated BLOCKED, floors that repeat from run to run past the brief's `differ` failing `grid.same` (#3265), a goal still reached with every cell one of the brief's `needs` names closed failing `grid.skipped` with the route (#3263), one more search a need a floor, and a need the working agent wrote (`by: "agent"`) refused before any run, and its flow form, which checks that a flow field leads every spawn down in cost to its target.

`catalog` (#194) checks a game's content tables in their one layout, table.layout@1, which `deep-catalog` packs: `catalog.refs` (every reference names a row), `catalog.reach` (a fixed point from the brief's roots, a recipe reachable once all its inputs and tools are), `catalog.economy` (no cycle of recipes and uncrafts gains a row, and with values no recipe gains past its margin), `catalog.bounds` (declared ranges hold), `catalog.copy` (every shown key has copy in every locale) and `scenario.reach` (each goal of a scenario's trigger rows can fire from its start, with its own search over the map). Each reads the catalogs its spec carries by hash and never runs the piece; an input the working agent wrote binds only its own checks. #832 adds a seventh that does run it, `catalog.dominance`: pairs of the named playtest's runs on one seed, with each row of a table on offer and with its `offers` cell at 0 (the replica plays that copy in the catalog's place), and a row whose presence raises the goal's share past the limit, its exact binomial interval clear of it, fails `catalog.dominant`; an interval holding the limit reads INCONCLUSIVE, and a pair that differs in more than the row's offers fails `catalog.unpaired`.

## Where new code goes

- `<name>/index.ts`: the plug-in, registering its kind; `<name>/deepbuild.json`: the manifest, whose `digest` is the folder's `packageDigest` and changes with every byte of the folder.
- `playtest/run.ts` plays and replays the runs (`model.ts` grows a model bot's replies, `soak.ts` reads a soak's windows); `legal.ts` is rules.legal and `edges.ts` logic.edges, each testing entries through a play's `probe` (`crates/deep-logic/src/probe.rs`); `reach.ts` is grid.reach, reading the grid only at the steps a play records it changing (`changes`); `judge.ts` judges a run from what it recorded; `bots.ts` takes or refuses each bot before any run (the first-party bots themselves run in the replica's play mode, `crates/deep-logic/src/grid_bot.rs`, so their search costs the piece no fuel and a run stays one play); `iface.ts` reads the play interface: its names, the lock's unit rule, ranges and goal expressions; `codes.ts` the codes with their meaning and fix; `kit.ts` its check.kind@1 kit, on the mazes in `fixtures/` (built by `DEEP_184_WRITE=1 cargo test -p deep-logic --test play_184 fixtures`).
- `catalog/layout.ts` opens a catalog from its bytes and the probe's record, `check.ts` holds what the kinds share (the result, the rows as one node array, a `makes` table's recipes), and each kind has its file: `refs.ts`, `reach.ts`, `economy.ts` (Johnson's search, capped at 100,000 cycles), `bounds.ts`, `copy.ts`, `scenario.ts`, and `dominance.ts` (catalog.dominance, which plays through `deep.canvas.play` and so stays out of the synchronous kit; its planted runners are `runDominance`'s); `kit.ts` is one check.kind@1 kit a kind, on the catalogs in `fixtures/` (rebuilt by `DEEP_194_WRITE=1` on `test/catalog.test.ts`).
- Tests: `test/`, outside each plug-in's folder so they stay out of its digest; `tests/acceptance/184` is never edited.

## What it may import

A plug-in folder is copied alone at install: at run time it imports only `node:` built-ins and its own files; types from `@deepbuild/conformance`. `kit.ts` imports the conformance runner's findings, and runs only from the tests and the preflight.

## Deviations

- The `.wasm` fixtures are built files in the tree, since the plug-in's digest covers every file its kit plays.
- No `package.json`: these are DeepBuild packages, not npm workspaces.
