## The surface

The tests reach the code only through these. Each is the base's own form or the delivery suite's, kept; the readings this job chose are marked.

- **The waiter**: `deep-hook claude-code waiter`, found as the delivery suite finds it: DeepBuild's `asyncRewake` entry under Stop in `~/.claude/settings.json` after `deep setup`. Its input is the Stop hook's JSON on stdin. **It delivered an answer** when it exits 2 with the answer on stderr, which is what wakes the session (`../../25/routes/README.md`, Routes); the answer is carried when stderr holds the picked option's label or ID.
- **An idle session with an open ask** is the delivery suite's asking session (SessionStart, a typed prompt, the agent's `deep_ask` through the session's own `deep mcp`, PostToolUse, its last words) and then its Stop, whose hold ends with nothing answered (the hub started with `DEEP_HUB_TEST_STOP_HOLD_MS=5000` and a 30 s `MCP_TOOL_TIMEOUT`, as that suite's `shortHold` and `noAskWait` do): the Stop goes through and the waiter Claude Code started at it is running.
- **`deep inbox answer <ask> <option>`** (#24): you answer, picking green. **The answer's acceptance** is that command's exit 0.
- **`~/.deepbuild/control.token`** under the test's home: the file the hub writes at launch. **Removed** is the file unlinked.
- **The record**, through `events.read` on a `cli` connection presenting the token this test read from the file while it was there and holds in memory, as the app holds it.
- **The hub's output**: what `deep hub run` writes to its stdout and stderr.
- **The Claude Code stand-in's `hook` command** (`{op: 'hook', event, payload, settings}`, documented at the top of `../../25/routes/fixtures/claude.mjs`), sent in AC2 with a settings file holding the waiter's entry alone under Stop (`helpers.ts`, `waiterUnder`), so A's Claude Code runs only the waiter with B's payload and no other Stop entry speaks for B from A's process.

No hello, method or reply of the waiter's new connection is written, sent or read by these tests: the issue leaves its wire form to the fix, so every waiter is the real binary, and the hub is only ever spoken to by it, by `deep` commands and by this suite's own `cli` connection.

## Readings where the issue leaves a choice

1. **"Removed after the hub starts" (AC1)** is removed after `deep setup` and after the session asked, and before the session's Stop, so before any waiter of it starts. Removed later, the base's waiter would already hold a connection it made with the token and would deliver; the issue says the base's waiter can't connect, so the file must be gone before the waiter first looks for it. The test checks the file is still gone when the waiter is running and after the delivery, so a program that writes it back is caught.
2. **How you answer with the file gone (AC1).** `deep inbox answer` reads the token from `~/.deepbuild/control.token` and the hub's address from `~/.deepbuild/config.json` (`hub.address`, the design's "Your hub, wherever it runs": a socket named there works). You hold the token from before the removal, as the app does from the hub's launch, so the test gives you a home of your own, `<tmp>/you`, whose `.deepbuild/config.json` names the hub's socket and whose `.deepbuild/control.token` holds the token read before the removal. No process of the session's tree has that home: the session's Claude Code, its hooks, its `deep mcp` and its waiter all run with `HOME=<tmp>/h`, where the file is gone. The criterion removes the file from where deep-hook would open it, not the token from you.
3. **Where a refusal is read (AC2, AC3).** The issue says the waiter "is refused, naming the binding" and "naming the process", and neither it nor the design says where the naming is shown: a refusal in this repo is an error@2 object on the hub's reply line, which only the refused process reads, and the wire form of the waiter's hello is the fix's to choose. Through the real binary a test can see that refusal only where the binary or the hub puts it, so the tests read all three places the refusal can surface, from the moment before the refused waiter starts: **the refused waiter's own stderr**, **each line of the hub's output**, and **each event the record gained that is a refusal** (its kind says `refused`, or its data holds an error@2 object, a `code` beside a `remediation`). The naming holds when any one of them holds the name. *Reading chosen here; none of the three is pinned by the issue or the design.* A fix whose hub names the binding or the process only on a reply line the waiter swallows shows it in none of these and fails the naming assertion; that would be a dispute for this job's redraft, with the place the fix does show it.
4. **"Naming the binding" (AC2)** is naming what the connection is bound to: session A's ID, or A's agent process by its PID (a number with no digit on either side). **"Naming the process" (AC3)** is the outsider's own PID, the process that connects. The hub's output and the refused waiter's stderr hold neither on their own (the waiter was told only B's session; the outsider's PID is sent on no hook line), and a record event counts only when it is a refusal, so a hook event that happens to carry session A's ID is not the naming.
5. **"Asks to wait on session B" (AC2)** through the real binary is the waiter given B's Stop payload while its process is a child of A's agent: the payload is the only thing that tells a waiter which session to ask for, and the process tree is what binds it. A waiter built to ignore the payload's session and wait on the session of its binding would ask for A, not B, and is never refused: it fails the naming assertion, and would be a dispute over whether such a waiter can "ask to wait on B" at all.
6. **"Never reaches A" (AC2) and the outsider (AC3)** are bounded: the refused waiter gets 3 s to connect and ask before you answer, and the test then waits until the answer went somewhere (at most 30 s) and at least 5 s past the answer's acceptance. Reaching is the waiter exiting 2, or its stderr carrying the picked option; for A it is also A's own waiter doing either, or A's Claude Code starting a wake that carries it.
7. **The answer is still delivered to its own session (AC2, AC3).** Each test's last assertion is that the session's own waiter, a child of its own agent, exits 2 with the answer: it shows the answer was there to take, so "never reaches" is not passed by a hub that delivers nothing, and it holds that refusing one waiter doesn't end the session's own (on the base the later waiter replaces it). It comes last, after the criterion's own assertions.
8. **The 2 s (AC1)** is one reading: from `deep inbox answer`'s exit (the answer's acceptance) to the waiter's exit 2, both read from the wall clock at the process that saw them. A waiter that hasn't delivered within 30 s fails whatever the load. A delivery later than 2 s on a machine whose 1-minute load average is over its core count is INCONCLUSIVE (the test is skipped saying so, with the reading and the load), never PASS; on a machine that isn't, it is a FAIL (the delivery suite's rule, `../../25/routes/README.md`, Timing).
9. **"deep-hook never opens control.token"** (Scope) has no criterion of its own. AC1 holds its consequence: with the file gone, a waiter that needs it fails. A deep-hook that opens the file when it is there and goes on without it is not caught here.
