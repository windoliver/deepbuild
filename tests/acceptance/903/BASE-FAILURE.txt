How the #903 acceptance suite fails at the base, d8c46f0d5 (main, "Merge pull request #2601").

This is a note, not a run. The machine this suite was written on was shared and loaded, so no Rust was built and no
test was run; each line below is read from the base's code. The implementer runs the suite unchanged at the base and
keeps the real output. What did run:

  $ npx tsc -p tests/acceptance/903/tsconfig.json
  (no output, exit 0)
  $ npx vitest list --root tests/acceptance/903
  (14 tests in 8 files)

What the base has and lacks, read from its code:

- The tour lives in the input module's session (crates/deep-canvas-input/src/session.rs: `tour_of`, `origin`,
  `advance`), driven by `deep-input input` (crates/deep-input/src/main.rs). `tour_of` reads `keys`, `idle_after`,
  `resume_after` and `loop`, ignores each key's `interp` and ignores `tour.pointer`. The session takes the tour board
  as it stands: a press and a toggle hit through `targets`, a slider through its `handle` (`press`, `knob`).
- The session has no `tour_pointer` op: `Session::op` answers any op it doesn't know with `bad_input` at `op`, and
  `deep-input` then answers the whole line {"ok": false, "code": "bad_input", "path": "op"}.
- `Planted::named` knows none of `tour_pointer_frame_clock`, `tour_pointer_glide_before_key`,
  `tour_pointer_takes_hits`: a line that names one answers {"ok": false, "code": "bad_input"}.
- The app plays no tour. `tour` is not in `ENVELOPE_KEYS` (crates/deep-canvas/src/document/mod.rs), and `check_envelope`
  (document/check.rs) raises `unknown_field` for any other key, "not a field of the document envelope": `deep_show`
  refuses a document that holds a `tour`. `eval` (crates/deep-show/src/main.rs) reads its fields by name, so it would
  ignore `tour_pointer: true` and answer with no `tour_pointer`.
