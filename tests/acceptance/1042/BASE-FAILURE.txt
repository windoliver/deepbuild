Faults of the suite that runs at the base showed, each repaired

1. The browser's flags. A first run, on November 25, of the suite as its second sitting left it: every test that
   opens a page was BLOCKED ("offers no WebGPU here (no navigator.gpu)"; "doesn't send the planted cookie"). The
   resolver's rule mapped every host to nowhere, this machine's loopback address among them, so no page of the
   suite's own server loaded. Loopback is now left out of the rule. A page the browser doesn't load, and a control
   request the stand-in source doesn't answer, are now BLOCKED by their own names, not as a missing adapter or a
   cookie that didn't travel.
2. A second page in one browser. In a run of November 25 with only that rule changed, the render test's second
   bundle was never ready within 180 s, with no notice and no page error. It was not the bundle: the browser's own
   session tells of every attach, the test's attach to a new page included, and the suite gave that event to the
   page opened before, which then took the new page's session for a context of its own, so the new page never heard
   its load event. A page now hears its own session and the contexts under it only. Confirmed on the stand-in: with
   the old dispatch a second page met "the second page hears its load event: nothing within 20000 ms" while the page
   itself was loaded and ready; with the new one a second and a third page were ready. The render test's wrong
   program was changed in the same sitting, from a face with no Han glyph to the face with its character map moved
   by one glyph, so that it is one the player loads and draws; the run above is the first of it.
3. The browser's own worker in a page's record. The first run of ac01's session on November 26 failed with the two
   failures quoted above and a third that was the suite's fault:
     "the page asked for chrome-extension://fignfifoniblkonapihmkfakmlgkbkcf/tts_extension.js, which is neither one
     of the bundle's own files nor a declared public source (request, the browser's record)"
   Some time into a session the browser starts a worker of an extension it ships. The suite takes every shared or
   service worker that starts under the browser into the record of the page now open, so that a worker a page
   registers can't ask for anything unseen, and it took this one too. A context whose script the browser serves from
   itself (`chrome-extension:`, `chrome:`, `chrome-untrusted:`, `devtools:`) is now left out of a page's record: it
   runs on, and the session's message names it, as the run quoted above does. A request a page itself makes to such
   an address is still in its record and still fails. Nothing else of the session changed between the two runs.

Two more were repaired on reading, with no run to show them: a wait that met its deadline named only the DevTools
command left unanswered, and now names what was awaited (the session's first failure above carries one); and a later
wait of the session that met its deadline with the play not over was dropped without a word, and is now a failure.
