== The base fact behind the redraft (read, not observed) ==

crates/deep-relay/src/relay.rs, `control`, lines 208 to 240:

- a `join` for an ID the relay holds (`Entry::Occupied`) takes the next free seat, whatever its `open` says;
- a `join` for an ID it doesn't hold is refused `unknown` when `open` isn't true, and opens the match when it is;
- once every seat is taken, `{"start": {"players": n}}` goes to every seat of that match;
- `forward`, `leave` and the `signal` branch send only to seats of the sender's own match.

packages/contracts/slots/relay@1.json says the same of `join` ("a second opening join of a held match joins it") and
`start` ("To every copy of a match once its last seat is taken").

With the first draft's third connections (../549/ac2-join-only.test.ts, lines 144 to 151), the third sends
{join: {match: near, players: 2, open: true}} and the fourth {join: {match: near, players: 2, open: false}}, `near`
being one string. By the code above the shipped relay answers the third `{"joined": {"player": 0}}`, the fourth
`{"joined": {"player": 1}}`, and then sends both `{"start": {"players": 2}}`. The first draft's line 181 lists each
`start` as a failure. (If the relay read the fourth's join before the third's, the fourth would be refused `unknown`
instead; the third's is sent before the fourth's connection is made, so that order isn't the likely one.)

With this file's third connections, each ID is named by one connection. By the same code the two that open are
answered `{"joined": {"player": 0}}`, the two that join `{"refused": "unknown"}`, and the relay sends none of them
anything else while the copies' match runs.
