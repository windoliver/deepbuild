# Acceptance tests for #79: the DeepBuild mark across the app, CLI, docs and site

These tests were drafted blind from issue #79 (its text as of October 20), `docs/technical-design.md` (the DeepBuild app row; "The reference Macs"; "Every task carries its own budgets"), `brand/README.md` (the kit's usage guide) and the base commit `30fba4b`, which is `origin/main`. The job was told the base was `2307398`; the checkout's HEAD is `30fba4b`, and nothing these tests read differs between them. Per AGENTS.md, the implementing agent doesn't edit them. A dispute goes to a blind redraft by this job.

At the base the kit already exists in `brand/`: the SVG masters, `DeepBuild.icns` built from `DeepBuild.iconset/`, `png/` with the tray templates, the favicons and web icons, `palette.json`, and `README.md`, which says no trademark search has been done. The README header already uses `brand/readme-light.svg` and `brand/readme-dark.svg` in a `<picture>`. The app (`crates/deep-app`) has a window and a menu-bar count but no icon, no title-bar mark and no welcome screen; the CLI (`packages/cli/src/main.ts`) prints a bare usage; there is no docs website and no social preview. The tests judge what each surface actually uses: the bytes a surface loads, the markup that names them, the output of `deep --help` in a pty, and the built binary. They never read the app's or the CLI's source, so the implementer may embed, copy or reference the kit however they like, as long as the bytes match.

## The surface (my choice, since none was named)

The issue names the surfaces but not where each one's asset is declared, where the trademark record and the screenshots go, or how the app's growth is recorded. I picked the smallest layout that fits the repo.

```
brand/surfaces.json          the surfaces manifest: one entry per use of the mark, with its kit file and screenshots
brand/trademark-search.json  the trademark search record
docs/web/head.html           the <head> fragment a docs site includes: favicon, web icons, web manifest
docs/web/site.webmanifest    the web manifest the fragment links, with its icons
docs/evidence/79/*.png       the screenshots the issue's Proof asks for, cropped to the surface
```

The values above are an example of the shape, not the answer; the kit files and sizes are the implementer's to choose within the rules below.

- **Surfaces.** Every one of these ten IDs needs at least one entry: `app-icon` (the macOS `.icns`), `menu-bar` (the status item's template image), `title-bar` (the mark in the window's title bar), `welcome` (the welcome screen's artwork), `cli-banner` (the image `deep --help` prints), `readme-light` and `readme-dark` (the README's `<picture>`), `docs-favicon` (the tab icon), `docs-web-icon` (`apple-touch-icon`, the web manifest's icons) and `social-preview` (the image for the repository's social card). A surface may have several entries (light and dark, 1x and 2x). Windows and Linux icons are "then" in the issue's scope and aren't required here.
- **`kit`** is a tracked `.svg`, `.png`, `.icns` or `.ico` under `brand/`. Committed or staged both count. The kit may gain files in this change (the scope includes the kit); a kit file is whatever is tracked under `brand/` at HEAD.
- **`use`** is the tracked file the surface actually loads: the path the README or the docs head references, the file the app's build embeds, the file the CLI reads. It may be the kit file itself. Its SHA-256 must equal the kit file's: byte for byte, never a redrawn, re-rendered or re-encoded copy.
- **`px`** is the height the mark (the D) is shown at, in points, a positive integer. It's required for every entry except an `.icns`, an `.ico` (each of their entries carries its own size) and the social preview. For a PNG, `px × scale` must equal the image's height, where `scale` is 1 (default), 2 or 3: a PNG shown at another size would be resampled. For an SVG, `px` is the implementer's statement; see Assumptions.
- **`shots`** names at least one PNG under `docs/evidence/79/` per entry: the issue's Proof. Each is tracked, under 1,000,000 bytes, at least 32×32, cropped to the surface so it shows no other app, name, clock or desktop (AGENTS.md: no personal data in evidence), and holds no text chunk with a home path. Two different surfaces can't share one image; entries of the same surface may. Every shot is pixel-scanned: no Signal pixel next to a white or paper pixel.
- **`app`** records the app-size budget: the merge base it was measured against (an ancestor of HEAD), the reference Mac it was measured on by `sysctl hw.model` and `sw_vers -buildVersion`, the date, and the stripped release binary's size at the merge base and at HEAD, measured as `docs/spikes/337/measure.mjs` measures the app: `cargo build --release -p deep-app`, a copy of `target/release/deep-app` run through `strip`, its size in bytes.

### `brand/trademark-search.json`

```json
{
  "mark": "DeepBuild",
  "searchedOn": "2026-10-2x",
  "searchedBy": "<a firm, a service or a role; no personal data>",
  "registers": [
    { "register": "USPTO", "database": "<optional: which search tool>", "queriedOn": "2026-10-2x", "terms": ["DEEPBUILD", "DEEP BUILD"], "classes": [9, 42],
      "hits": [{ "mark": "<the hit>", "owner": "<optional>", "status": "live | dead | pending | …", "classes": [9], "similarity": "identical | similar | unrelated", "note": "<optional>" }] }
  ],
  "conclusion": { "status": "clear | proceed-with-risk", "reason": "<why, from the hits; at least 20 characters>", "decidedBy": "<required when proceeding with a risk>" }
}
```

At least one register, each searched on a date not in the future with a term matching `deep build` (spaces optional, any case) in Nice classes 9 and 42, with its hits listed (an empty list when none). The conclusion must let the mark out: `clear`, or `proceed-with-risk` with whoever decided named. Any other status, such as a conflict, fails: the criterion is that the search is done *before* the mark is used outside the repo, and the README, the docs and the social preview are outside. `brand/README.md` must no longer say "No trademark search has been done" and must point at `trademark-search.json`. Neither file holds a home path or an email address outside `example.*`.

## How to run

Node 24 (`packages/cli/package.json` asks for 24.22 or later; `main.ts` runs through Node's type stripping). On macOS, which these tests assume for `script(1)`, `sysctl`, `sw_vers` and `strip`.

- Fast tests, no build, no network, no display: `node --test tests/acceptance/79/mark.test.mjs`. They take about a second, most of it four runs of `deep --help`.
- Live tests, which build the app and need Cargo's registry (the network once on a cold machine): `node --test tests/acceptance/79/mark.live.test.mjs`. The first builds the debug app. The second, on a reference Mac only, builds the release app at HEAD and at the recorded merge base (the merge base in a scratch tree, with `target/acceptance-79-base` as its target directory so Cargo's cache stays warm), which takes minutes.
- The checks' own tests, which plant wrong files and records and pass at the base: `node --test tests/acceptance/79/checks.test.mjs`.
- Everything: `node --test tests/acceptance/79/*.test.mjs`.
- The preflight's `tests/*.test.mjs` pattern doesn't reach this folder.

### How I checked the tests can pass and fail

At the base all 11 tests fail, each on its own assertion (`BASE-FAILURE.txt`): nine on the missing manifest or record, the docs test on the missing `docs/web/head.html`, and the CLI test on `deep --help` printing no inline image under iTerm2 or kitty. `checks.test.mjs` runs the checks on the kit as it stands and on planted wrong inputs built in memory: every kit raster of 16 and 32 px measures as the small cut and every larger one as the regular cut, including the `.icns` and `.ico` entries; the regular cut box-downsampled to 16, 32 and 64 px is caught; a lockup isn't judged as a symbol; the small and full SVG masters read as small and regular; the Ink tiles keep Signal off white and off transparent; the colour symbol and the colour lockup over white or paper are caught and over Ink are not; a Signal fill planted in `readme-light.svg` is seen; a complete search record holds and each wrong one above fails; a budget record of growth under 200 KB on a reference Mac holds and each wrong one fails; and a banner carrying a kit image once on its first line holds while another file, a missing image, an image on line 2, an image for a plain terminal and escapes in a pipe each fail. No synthetic manifest was planted in this checkout; the record-level checks (`manifestProblems`, `docsProblems`, `shotProblems`) were read against the kit and README at the base by hand through the helpers and not kept.

## What cannot be proven on this machine, or by these tests

- **The app's surfaces need a build.** The fast tests can't tell whether the app embeds anything; only `mark.live.test.mjs` can, and it needs Rust 1.95 or later (the crate's `rust-version`), Cargo's registry and gpui-kit's git checkout. On a cold machine that's the network once. At the base both live tests fail before building, on the missing manifest.
- **The app's size budget counts only on a reference Mac.** This draft ran on a 13-inch MacBook Air (`Mac15,12`), which the design names, so the live test can count here. On any other Mac it fails with `INCONCLUSIVE`. The design's mains-power, Low Power Mode and thermal conditions apply to timing and memory budgets; a stripped binary's size doesn't move with them, so the test doesn't check them. It does record the macOS build.
- **"In the local preflight."** The perf lane (`scripts/perf.mjs`, `benchmarks/budgets.json`) measures a command's time and peak memory in 20 rounds against the merge base; it has no binary-size metric, and a size lane would need a release build of both sides, which the preflight doesn't do. #337 measured the app's size by hand with `docs/spikes/337/measure.mjs` and recorded it. These tests follow that: the `app` record is the preflight's reading, the live test re-measures it. Whether a lane must re-measure it at release is for a redraft or the owner.
- **What a screenshot shows** isn't checked beyond the Signal scan: that the dock really shows the icon, that the title bar shows the mark, that the social card renders, is for the person reviewing the proof. The tests check only that each shot exists, is a small distinct PNG and puts no Signal on white or paper.
- **An SVG's `px`** is the implementer's statement; the tests can't measure how large the app draws an SVG. `menu-bar`, `cli-banner` and `docs-favicon` can't be over 24 px by nature, so those are held to it regardless; a `title-bar` entry declared at 28 px with the regular cut passes, and a shot shows whether that's honest.
- **The social preview's provenance.** A composed raster can't be traced to the kit's vectors by hash; only that the kit holds it, its size and its Signal placement are checked. Whether its lockup is the kit's is for the reviewer.
- **The trademark search itself.** The tests check the record's shape and that it lets the mark out, not that the registers were really queried or the hits are complete. The issue's Proof asks for the search result; the record is that result.
- **Windows and Linux app icons** aren't tested; the issue's scope puts them after macOS.

## Assumptions a redraft may revisit

- I picked the manifest, its field names, the ten surface IDs, the docs fragment and web manifest, the evidence folder, the search record's shape and the `app` record. A surface that doesn't fit (a bundle's `Contents/Resources/DeepBuild.icns` instead of an embedded `.icns`, say) is a case for a redraft, not for editing the tests.
- "Checked by each asset's hash" is read as byte equality with a kit file, so the app embeds the kit's files as they are. An app that decodes the `.icns` at build time into raw pixels would be using the kit's file in a sense, but no hash could show it.
- "24 px and below" is read in points: an @2x raster shown at 16 pt counts as 16 px, so `icon_16x16@2x.png` (`ic11`) and `trayTemplate@2x.png` must be the small cut, while `icon_32x32.png` and `ic05` at 32 pt need not be, as `brand/README.md`'s "for 16 and 32 px" allows either way.
- The small cut is recognized by geometry, not by file name: the kit's small-cut path commands in an SVG, and a square D in a raster. A redesigned small cut that isn't square, or whose SVG path is written differently, would need a redraft.
- "Nothing puts Signal on white or paper" is judged on the files and shots the surfaces use, with grounds as the table above states. A raster's Signal must have no light or transparent neighbour unless the surface's ground is known dark; an SVG's dark first fill stands in for an Ink tile. These are proxies: a Signal pixel one ink pixel away from white passes, and an SVG whose first fill doesn't cover its box passes.
- The README's light image may carry no Signal at all, since GitHub's light theme is white, and the dark source may, since GitHub's dark theme is dark. GitHub's exact colours aren't read.
- The CLI banner's terminals are iTerm2 and kitty, the two inline-image protocols a Node CLI can speak without a dependency; sixel isn't required. "Where the terminal can show it" is read from the terminal's own identification; the banner is the first line of `deep --help`, names DeepBuild in text, and `--version` and `explain` are untouched. A piped `deep --help` prints no escape at all, so the existing vitest tests still hold.
- The trademark record needs at least one register, not a professional search; `brand/README.md` asked for a professional one before launch, and `searchedBy` records who ran it. The conclusion must allow use outside the repo, since the README and social preview already are.
- 200 KB is 200,000 bytes, as `benchmarks/budgets.json` counts a megabyte as 10^6. The embedded total is measured twice: the kit files' sizes (exact and machine-independent) and the stripped binary's growth (what the issue asks). Both must be under.
- The privacy checks read this machine's `HOME` and git email at run time and never store them.

**Redraft, 2026-10-20.** The privacy rule on `brand/surfaces.json` and `brand/trademark-search.json` (`privacyProblems`, under `#79.816c9037` and `#79.c744da3f`) was redrafted blind from AGENTS.md ("No secrets or personal data in code, fixtures, logs or evidence. Redact."), the rule above ("Neither file holds a home path or an email address outside `example.*`") and what this README says the two files hold. It rules: a home path is a user's home folder written out at the start of a path (`/Users/<name>`, `/home/<name>`, `<drive>:\Users\<name>`, or this machine's `HOME`, read at run time and never stored); a `home` segment inside a register's URL is not one, and `~` is the design's redaction of a home folder, so it passes. An email address is a local part and a domain standing on their own; an `@` after a `/` in a path, or one starting a raster's scale suffix (`png/trayTemplate@2x.png`, which the manifest above lists), is a file name; addresses under `example.*` or a subdomain of it are allowed, and any other fails, reported with its local part cut to one letter. The git email is no longer read: an `example.*` address is nobody's. `checks.test.mjs` plants the kit's `@2x` names, a register URL with a `home` segment and `example.*` contacts as legitimate, and home paths on macOS, Linux and Windows and personal addresses in six spellings as wrong.
