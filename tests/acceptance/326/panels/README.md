# Acceptance tests for #326, group "panels": one record reader, its guard, and panels kept in their slot

These tests cover four of #326's seven criteria, AC4 to AC7: the app's one record reader and the guard that keeps it the only one, a panel package with a Git dependency, the four `registerView` faults, and nothing drawn over the question card. AC1 to AC3 (Set up, notifications, States people see) are other groups' work.

They were written blind from issue #326 (its text as of October 28, 2026: Scope, the seven criteria, Proof, Depends on), `docs/technical-design.md` (the DeepBuild app and Trusted ring rows of "One hub per user, a tiny hook client, and extensions in-process"; "First-party extensions that ship on by default"; the Replica subsection; the App API row, with its sentence on the one record reader and its guard in the app's local preflight; "One event log" and `log_pos`; "How we know version 0 works" and its Dogfooding bullet), and the base commit `debda22` (origin/main), where nothing of #326 is implemented: `crates/deep-app` (`src/record.rs`, the base's record reader; `src/hub.rs`; `src/views.rs`; `src/lib.rs`), `crates/deep-replica`, `packages/hub/src/server.ts` (the App API's method names), `scripts/lanes.mjs`, `scripts/preflight.mjs`, `scripts/checks.mjs`, `scripts/proof*.mjs`, and the conventions of `tests/acceptance/34/README.md` and `tests/acceptance/338/README.md`. No implementation of #326 was read. Per AGENTS.md the implementing agent doesn't edit these files; a dispute goes to a blind redraft of this job.

**Who wrote what.** The Rust files (`common.rs`, `hub.rs`, `panels.rs`, `planted.rs`) and `fixtures/**` come from an earlier blind job for this group that was stopped before it finished; they were copied unchanged. The guard's tests (`guard.test.mjs`, `guard-judge.mjs`, `guard.wrong.test.mjs`, `wrong/**`), this README and `BASE-FAILURE.txt` are this job's. A first draft of the guard files was already in the copied folder, of unrecorded provenance; this job reviewed it against the issue, the design and the base, and rewrote it (plants declared as real modules, a plant through a constant, the exit code and FAIL line pinned, the preflight wiring judged by a function with wrong lane tables, three more wrong guards).

## The surface (my choice where the issue names none)

### The record reader, `deep_app::record`

- `deep_app::record::RecordReader::open(socket, token_file)` as at the base (#34).
- `deep_app::record::install(reader: RecordReader)`: makes that reader the app's one record reader, the one every view in the process draws from.
- `deep_app::record::poll(timeout: Duration) -> Result<(), HubError>`: lets the installed reader handle what the hub sent within `timeout`, the way `RecordReader::poll` does, and feeds every view from it.
- The views keep the base's surfaces: `deep_replica::shell::open_shell(&Layout::shipped("needs-you" | "session"), cx, ..)`, Needs you's rows as accessibility nodes named `ask:<id>` (`deep_replica::snapshot::from_observed`), and the session page's count as the canvas item `session-readout` (`deep_app::canvas::items`).

### The guard, `scripts/record-reader-guard.mjs`

- **Run as** `node scripts/record-reader-guard.mjs [--root <dir>]`. It checks every `.rs` file under `<dir>/crates/deep-app/src`, at any depth. Without `--root` it checks the checkout it's run in; preflight runs it from the repo root.
- **What counts.** A module "subscribes to the stream or calls the reads" when it names one of the hub methods the base's record reader and the hub's App API use: `stream.subscribe`, `events.read`, `inbox.read`, `sessions.read`, `changes.read`, `evidence.read` or `numbers.read`, whether in the call itself or held in a constant first. The one record reader's module is the only one allowed them; which file that is is the implementation's choice, and the guard must pass the app as it stands.
- **Output and exit.** On a clean tree: exit 0 and no line starting `FAIL`. For each other module that names one: a line starting `FAIL ` that names the module's file by its path under the root (for example `FAIL record reader: crates/deep-app/src/planted_view.rs calls stream.subscribe`), and exit 1. The `FAIL ` prefix is what `scripts/lanes.mjs`'s `runLanes` lifts into the lane's failure line.
- **Wiring.** A lane of `scripts/lanes.mjs`'s `checks` (the local preflight, `scripts/checks.mjs`; not `releaseLanes`) has a command whose arguments end with `scripts/record-reader-guard.mjs`. The lane runs on every change, or at least on every change under `crates/deep-app/src/` (no `paths`, or a `paths` entry ending in `/**` that covers it). Its command, run from the repo root as `runLanes` runs it, exits 0, and it doesn't point `--root` anywhere but the checkout.

### Panels, `deep_replica::kit::panel` and the shell

- `deep_replica::kit::panel(dir: &Path) -> Verdict`: `panel@1`'s install check on the package in `dir`, with the base's `Verdict { pass, names }`. A refusal is `pass: false` and its message in `names`.
- `deep_replica::shell::open_with_card(cx, card: Bounds<Pixels>, panel: Option<&Path>) -> (AnyWindowHandle, Bounds<Pixels>)`: the app's shell in the reference window (1512 x 982 points at 2x, `deep_replica::shell::window_options`), with the question card presented at `card` and, when given, the package in `panel` mounted past install in the sidebar slot; it returns the window and the slot's bounds. With no panel, the shipped sidebar fills the slot.
- `deep_app::mount_panel(&runtime, dir, window, cx)`, as at the base, for loading a package past install; with a manifest that lists a Git dependency it must reach no host and leave nothing under `$GPUI_SHELL_HOME/cache`.

### The card and the slot

The card sits at (264, 4), 1244 x 854 points, right of the 260-point sidebar slot, so a dialog in the middle and a notification at the top right both land inside it. A capture's card interior is the card's device rect less 2 pixels on each side (farther than 1 device px from its edge). Every fixture paints in magenta (`#ff00ff`), which nothing else uses. The fixture packages are under `fixtures/`: `fetched-dependency` (AC5, its manifest's dependency `pad-326` on a local listener), `faults/{network,program,focus,draw}` (AC6), `components/{dialog,popover,tooltip,context-menu,dropdown,notification,command-palette,twice-slot,grows}` (AC7). The tests copy each into `/tmp/da326p-<pid>-<n>` and write the listener's port and a marker file's path over `__PORT__` and `__MARKER__`.

## How to run

From the repo root, with the repo's Node (24.22.0) first on `PATH`:

```sh
node --test tests/acceptance/326/panels/guard.test.mjs          # AC4's guard; fast, no build
node --test tests/acceptance/326/panels/guard.wrong.test.mjs    # the guard judges against wrong guards; passes at the base
cargo test --locked -p deep-replica --test acceptance_326_panels           # AC4's app half, AC5, AC6, AC7
cargo test --locked -p deep-replica --test acceptance_326_panels_planted   # the wrong programs; pass at the base
```

- The two Rust suites are wired into `crates/deep-replica/Cargo.toml` by `[[test]]` entries `acceptance_326_panels` and `acceptance_326_panels_planted`, both `harness = false`: AppKit needs the main thread for offscreen Metal captures, so each prints libtest's result lines itself. A test name given after `--` filters them. They need macOS; elsewhere they print INCONCLUSIVE and exit 1. The first build compiles gpui-kit (several minutes on a cold target).
- `cargo test --workspace`, in the unit lane, builds and runs both Rust suites too. The preflight's `tests/*.test.mjs` pattern doesn't reach the `.mjs` files here; the proof lanes run `guard.test.mjs` as tagged tests.
- The guard tests copy `crates/deep-app/src` to `/tmp/da326g-guard-*` (the OS temp dir where there's no `/tmp`) for each run and remove it; they never write to the repo. The Rust suites use `/tmp/da326p-*` and set `GPUI_SHELL_HOME` to one of them. Nothing here starts a process it doesn't stop, and nothing is stopped by name or port.

## What the base commit has

At `debda22`, `guard.test.mjs` fails both tests for the missing surface: there is no `scripts/record-reader-guard.mjs`, and no lane runs it. `acceptance_326_panels` doesn't compile: `deep_replica::kit::panel`, `deep_replica::shell::open_with_card`, `deep_app::record::install` and `deep_app::record::poll` don't exist, so its five tests fail before they run. The wrong programs pass at the base: `acceptance_326_panels_planted` and `guard.wrong.test.mjs`, since they test the tests. `BASE-FAILURE.txt` holds the run, trimmed to each failure's reason.

## Assumptions a redraft may revisit

- **The guard's name, place and output.** The issue says only "a guard in the app's local preflight". I picked `scripts/record-reader-guard.mjs`, `--root`, exit 1 and a `FAIL ` line naming the file by its path under the root. A guard folded into another script (`repo-rules.mjs`, `canvas-lint.mjs`) would fail these tests though it meets the criterion.
- **"Subscribes to the stream or calls the reads"** is read as naming one of seven hub methods in the module's source: `stream.subscribe`, `events.read` (the refetch the base's reader calls) and the App API's five reads from `server.ts`. `status.read`, which the hub also serves the app, isn't in the design's list of App API reads and isn't planted; a guard may count it. A module that reaches the hub some other way (a raw socket, a method name built at run time) isn't planted.
- **"The app" is `crates/deep-app/src`.** `crates/deep-replica`, `crates/deep-app/screens.rs`, its `tests/` and the JavaScript panels under `crates/deep-app/panels` aren't scanned or planted. Panels run in gpui-shell with no hub socket.
- **A planted module is a real module**, declared in the copy's `lib.rs` (`pub mod planted_views { pub mod nested_view; }` for the nested one), so a guard that walks the crate's module tree passes these tests as a file scan does. The plants use the base's `crate::hub::HubClient::call`; all ten together compile at the base (`cargo check --locked -p deep-app --lib`, run once by hand with them in place, then removed). The tests themselves don't compile them.
- **The lane may be scoped to the app's paths.** A lane with no `paths`, or one whose `paths` cover `crates/deep-app/src/`, counts as the local preflight running the guard, since a change that plants a module touches that folder. A lane only in `releaseLanes` doesn't count.
- **The same `log_pos`** is observed through what the two views show: Needs you's open rows and the session page's count of its session's open asks, equal after each frame once polled, plus the hub seeing one subscription. A wrong app that keeps two readers in step by polling both at once would pass the first and fail only the second.
- **The Rust surface** (`record::install` and `poll` as free functions, `kit::panel`, `shell::open_with_card` with an `Option<&Path>` panel in the sidebar slot, the card's rect, the refusal words) is the earlier job's choice, kept unchanged. Its assumptions on refusal words: a fault's refusal contains the fault's word (`network`, `program`, `focus`, `draw`); a component's contains its name or gpui-shell's (`popup` for the context menu, `command` for the palette), and the two layouts' say `outside its panel`.
