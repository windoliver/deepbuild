# Acceptance tests for #569: proof lanes in the preflight

Written first, blind, from issue #569 (its text as of October 22, 2026: Scope, the 12 acceptance criteria, Proof, and Depends on #12, #28, #246), `docs/technical-design.md` (How runs become one of five verdicts: Fail before, pass after, Failing on an assertion, Numeric contracts, Protection; Lifecycles; How we know version 0 works: Property tests, The cheat corpus, Fault injection, Verdict changes are shown before merge, Criteria to tests, Wrong programs, The edit guard, Dogfooding, Built to be hard to get wrong, Where each layer runs; Decisions), `AGENTS.md`, the house style of `tests/acceptance/246/` and `tests/acceptance/86/`, and the base commit `7fc4f14` (`origin/main`, no proof lanes). The implementing agent doesn't edit these files (AGENTS.md, Proof); a dispute goes to a blind redraft by this job.

## Run

```sh
node --test 'tests/acceptance/569/*.test.mjs'
```

Node 24.22 or newer, git with SSH signing (2.34 or newer), `ssh-keygen`, and this checkout's `node_modules` (`npm ci` once: the crash-suite stand-in runs on its vitest). No network, no `gh` login. Every test builds its own scratch git repositories under the system temporary folder (realpathed) and removes them afterwards; nothing is written into this checkout. On the base the 48 tests take a few seconds and all fail, each because `scripts/proof.mjs` doesn't exist or `scripts/lanes.mjs` has no proof lane (`BASE-FAILURE.txt`, local paths redacted). With the lanes in place the suite should take a few minutes at most, mostly the merge-base runs and, where StrykerJS is installed, the mutation runs.

## Surfaces

The tests reach the implementation only through what the issue and the design name, made concrete in the Readings below:

- **`node scripts/proof.mjs [--release] [lane ...]`**, run as a process from this checkout with its cwd at a scratch repository. This is "the preflight's" proof lanes: the guard, fails before, the trace lane, the mutation lane, the lifecycle enumerator, the crash suite and the verdict replay.
- The preflight wiring (`preflight.test.mjs`): `package.json`'s `preflight` and `release:check` scripts, read. Each must be `scripts/preflight` behind its leading `KEY=value` assignments: none for `preflight`, and `DEEP_PREFLIGHT=release` for `release:check`, the base's release preflight. `scripts/checks.mjs`, the lane runner `scripts/preflight.mjs` calls, runs in a child `node` process: once without `DEEP_PREFLIGHT` (local), and once with the environment parsed from `release:check`. A `--import` preload swaps `spawnSync` for a recorder that prints each lane command and reports success, so no lane really runs. Git still runs, read-only, so path-gated lanes gate as they would. The local run must hold exactly one `scripts/proof.mjs` command, with no arguments. The release run must hold exactly one, with `--release` and no lane names, and none without `--release`. The full preflight (10–25 minutes) isn't run.
- **Files in the repository checked**, in the layouts below: tagged tests, goldens and JSON Lines fixtures, `AGENTS.md`, `docs/technical-design.md`, `tests/acceptance/<issue>/twins.json` and its twin folders, lifecycle tables under `packages/contracts/schemas/`, the hub's `packages/hub/src/vfs.ts`, the crash suite's files, the verdict engine's package and the replay cases under `tests/fixtures/`.
- **Git objects**: commits with `Closes #n` or `Part of #n`, and SSH-signed approval tags.
- **Environment**: `DEEP_PROOF_ISSUES` (a folder of issue bodies) and `DEEP_APPROVERS` (the approvers file).

Scratch git commands run with `-c user.name=Fixture -c user.email=fixture@example.invalid -c commit.gpgsign=false -c tag.gpgsign=false -c core.hooksPath=/dev/null`. Each scratch repository has the merge base committed on `main`, `refs/remotes/origin/main` pointing at it, and the change as one or more commits on branch `change`, sometimes with uncommitted edits on top. The planted issue is `#9001` (and `#9002` for an unrelated one); its tags are computed at runtime from its criteria's text, so no file here carries a literal tag a real issue's trace lane could read.

## Readings where the issue leaves a choice

1. **The entry point.** A new script, `scripts/proof.mjs`, runs the proof lanes on the git repository at its **cwd**, never on the checkout it sits in. Its lanes are `guard`, `before`, `trace`, `mutation`, `lifecycle`, `crash` and `replay`. With no lane named it runs every lane of its mode; with lanes named it runs only those, plus the lanes they read (`trace` reads `before`; `before` reads `mutation` only when `mutation` runs too). Local mode (no `--release`) runs `guard`, `before` and `trace` on every change, `lifecycle`, `crash` and `replay` only on a change that touches their paths (Readings 14 to 16), and `mutation` never. `--release` adds `mutation` and runs `lifecycle` and `crash` in full whatever the change touched. It exits 0 when it printed no FAIL, BLOCKED, INVALID or INCONCLUSIVE line, and 1 otherwise.
2. **The preflight runs it.** The local preflight runs `scripts/proof.mjs` exactly once with no mode. The release preflight is the base's own, `npm run release:check`, which is `DEEP_PREFLIGHT=release scripts/preflight`; it runs `scripts/proof.mjs` exactly once with `--release` and never without (Surfaces: the preflight wiring). Redrafted once against the base that holds #684's release preflight; the first draft asked for `scripts/preflight --release` and a `releaseChecks` export.
3. **Output.** Lines go to stdout. Each finding is one line, `<STATE> <lane>: <detail>`, with STATE one of FAIL, BLOCKED, INVALID or INCONCLUSIVE, and the next line is its `  Fix: ` line, as in every other lane. A lane that ran and found nothing wrong prints at least one `PASS <lane>: ` line. The before lane prints a `PASS before:` line for each test it proved, naming the test and the wrong program it failed on. The mutation lane's survivors print as in Reading 13.
4. **The change and the merge base.** The merge base is `git merge-base HEAD origin/main`, as perf takes it; without `origin/main` every lane is BLOCKED, naming it. The change is the commits `git rev-list --reverse --first-parent <base>..HEAD`, each read as its diff against its first parent, then the worktree's uncommitted changes and the untracked files git doesn't ignore, read as one more commit that no approval can cover. Files are what `git ls-files --cached --others --exclude-standard` lists, never what a folder walk finds. A run leaves the repository's worktree list, refs and `git status --porcelain --ignored` as they were: merge-base and twin checkouts are temporary folders outside it, made from `git archive`, and removed after the run.
5. **The issue a change closes.** It is the issue named by a line `Closes #n` or `Part of #n` in any commit message of the change. Its body comes from `$DEEP_PROOF_ISSUES/<n>.md` when that variable names a folder, and otherwise from `gh issue view <n> --json body`; a body that can't be read makes the trace lane BLOCKED, naming the issue. Its criteria are the `- [ ] ` or `- [x] ` lines under `### Acceptance criteria`, up to the next heading. A criterion's ID is `#<n>.<h8>`: the first eight hex digits of the SHA-256 of its text, trimmed, white space collapsed to one space and the leading `- [ ] ` dropped. This is the normalization every earlier acceptance suite used (the command in `tests/acceptance/48/README.md`; it gives `#56.6526364c` and `#338.6257cd5b` for those issues' criteria and the `#569.…` tags here). The design says the text is "normalized … as open items are named", which also applies Unicode NFC, case folding and drops trailing punctuation; that would change every existing tag, so these tests follow the repo's practice (see Contradictions). A change that names no issue has its every tagged test guarded; one that names two issues makes the trace lane BLOCKED.
6. **Tests, names and tags.** Test files are `*.test.mjs`, `*.test.js` and `*.test.ts` under the declared test paths (`testPaths` in `scripts/lanes.mjs`), and Rust tests under `crates/*/tests/`. `.test.mjs` and `.test.js` files run with `node --test`, `.test.ts` files with the repo's vitest, Rust tests with `cargo test`; the scratch repositories use only `node --test`. A test carries a tag when its full name contains `#<n>.<8 hex digits>`. The trace and before lanes take names from the runner's report; the guard reads them from the source: an `it(`, `test(` or `describe(` call (with `.skip`, `.only` or `.todo`) whose first argument is a string literal, the test's span being the lines from that call to its closing parenthesis. Every line, and every approval, names a test as `<repo path> › <full name>`, so naming a test also names its criterion.
7. **What the guard guards.** Over every commit of the change (Reading 4), for the tags of the issue the change names:
   - **Tests.** A removed or changed line inside a tagged test's span is an edit of that test: adding `it.skip`, deleting the test and rewriting its expected value are all removed or changed lines. A removed or changed line outside every test's span, in a file that holds tagged tests, is an edit of each tagged test in the file. A removed or changed line inside an untagged test's span is free, and so is every added line, so a change that only adds tests passes. A deleted file is an edit of each tagged test it held.
   - **Goldens, fixtures and expected outputs.** A file under the test paths that isn't a test file is covered when it carries a tag of the issue, or when its path, from the repo root or from the test file's folder, with or without `./`, appears in a tagged test's span (or anywhere in a file of tagged tests, which covers it for each of them). Any removed or changed line in it, or any change to a binary one, is an edit, and its FAIL line names the file and each tagged test that reads it.
   - **Decisions.** In `AGENTS.md`, every line from `## The four invariants` to the next `## ` heading; in `docs/technical-design.md`, every table row (a line starting `|`) from `## Decisions` to the next `## ` heading. A removed or changed line there is an edit named `<file>:<line>`, the line's number in the merge base's file. Lines elsewhere in those files are free.
   - Each unapproved edit prints `FAIL guard: <test, file or file:line>: <what changed>` with its Fix line; the detail names the test (so its criterion) or the file and line.
8. **Approved proposals, and why an agent can't forge one.** An approval is an annotated git tag under `refs/tags/deep/approved/`, pointing at one commit of the change, signed with SSH (`gpg.format=ssh`), that `git -c gpg.ssh.allowedSignersFile=<approvers> verify-tag <tag>` accepts, where `<approvers>` is the SSH allowed-signers file `$DEEP_APPROVERS` names, `~/.deepbuild/approvers` by default. Its message holds one line `Approves: <item>` per item: `<path> › <full test name>` covers that one test; `<path>` covers every guarded edit in that file; `replay sha256:<hex>` is a yes on a replay list (Reading 16). A commit is **its own proposal** only when its diff against its first parent touches nothing but the files its approval's items name. The guard judges each commit on its own: a guarded edit passes only when its commit is its own proposal and an approval item names it, so an approval for one test lets no other test's edit through, and an approved commit that also carries code covers nothing. A tag that is unsigned, is signed by a key the approvers file doesn't list, or points at another commit is no approval, and the guard reads no file in the tree as one. Why this can't be forged by the change under test: the change consists of commits and files, and an approval is a signature by the maintainer's private key, checked against a list of keys that lives outside the repository and is named by whoever runs the preflight. No commit, file or message in the change can make one (invariant 3).
9. **Tolerances only tighten.** The tests use a JSON Lines fixture, one case per line: `{"case", "criterion", "tolerance", "input", "expected"}`, the case carrying its tag in `criterion`. Values are compared as numbers and printed as written in the file.
   - **In place**: the same `case` with a larger `tolerance` is refused even inside an approved proposal: `FAIL guard: <fixture>: case <name>: tolerance raised from <old> to <new>`, holding the fixture's path and both values as written (`1e-6`, `1e-4`). A smaller value is an ordinary guarded edit: it passes as an approved proposal.
   - **A new looser case**: an added case whose criterion matches a case the fixture held at the merge base, with a tolerance larger than that criterion's smallest, passes only inside its own approved proposal whose commit message holds `Old bound: <old as written>`, `New bound: <new as written>`, and a line `Runs:` followed by one line starting `<case name>:` for each of the two cases, and only when its `input` equals the old case's. Without approval it fails, naming the fixture.
   - **The old case** goes only by its own approved proposal: a proposal that adds a looser case and also removes or changes a case of the same criterion fails, naming the fixture.
   - Other bounds the Scope names (an accumulation type narrowed, a pixel share widened) follow the same rule, but no test here reaches them.
10. **Fails before.** The before lane runs each new or changed tagged test, and each test tagged with a criterion of the change's issue, on the merge base: a temporary checkout made from `git archive <base>`, with the test's own files taken from the change (its file and every file under its folder, which holds its fixtures, goldens and twins). When that checkout has a `package.json`, `npm ci --no-audit --no-fund` runs in it first, as perf's copies do; when that fails, each test of the run is `BLOCKED before: <test>: npm ci failed: <first error line>`, never a pass and never a FAIL of the test. Then, by where each test failed (from the runner's report, never its output):
    - failed at its assertion (the framework's own assertion failure, `AssertionError`, `ERR_ASSERTION` or a matcher's result, thrown at an assert or expect line in the test's own files): `PASS before: <test>: failed on the merge base at its assertion`;
    - passed: `FAIL before: <test>: passed on the merge base`;
    - wasn't collected, or failed elsewhere (a missing import, a `TypeError` from calling a function the fix adds, a hook): `FAIL before: <test>: failed on the base before its assertion (<cause>)`, the cause naming the error, such as `ERR_MODULE_NOT_FOUND` with the missing module, or `TypeError: cart.double is not a function`.
    The last two give way to a planted wrong program (Reading 11) or a mutant (Reading 13) the test fails on. The design calls a check that can't prove its fix INVALID, so these lines may read `INVALID before:` instead of `FAIL before:`; the tests accept either, and the run exits 1 either way. The quoted phrases are exact.
11. **Planted wrong programs.** A criterion names its twins in `tests/acceptance/<issue>/twins.json`, `{ "<criterion ID>": ["<twin name>", …] }`. A twin is the folder `tests/acceptance/<issue>/twins/<twin name>/`, whose files replace the files at the same repo paths. Each test tagged with that criterion runs in a temporary checkout of the change with the twin put in place; one that fails there at its assertion is `PASS before: <test>: failed on <twin name> at its assertion`. One that fails on none of its criterion's twins at its assertion, and didn't fail on the merge base at its assertion, and kills no mutant, is `FAIL before: <test>: <criterion ID>: fails on neither the merge base nor its planted wrong program`, naming the criterion.
12. **The trace lane.** It reads the change's issue (Reading 5) and every test file the repo lists, and collects each tag `#<n>.<8 hex digits>` of that issue. A tag that names no criterion the issue now holds fails: `FAIL trace: <tag> names no criterion of #<n>` (with the test). A criterion is proven when one of its tagged tests ran in this run on the change and passed, wasn't skipped or todo, and failed on a wrong program in this run (a `PASS before:` line, or a mutant it killed). A change that says `Closes #n` with any criterion unproven fails: `FAIL trace: Closes #n refused: this change is Part of #n; open: <ID>, …`, naming every unproven criterion and no proven one. A change that says `Part of #n` passes, `PASS trace: Part of #n; open: <ID>, …`. `Closes #n` with every criterion proven passes.
13. **The mutation lane.** It runs on demand (`node scripts/proof.mjs mutation`) and in the release preflight, never in the local one. It mutates only the lines the change adds, against the merge base, in the files it touches: StrykerJS on `packages/*/src/**/*.ts`, cargo-mutants on `crates/*/src/**/*.rs`. StrykerJS is `node_modules/.bin/stryker` in the repository checked; cargo-mutants is `cargo mutants` on `PATH`. A tool the change needs and that isn't there makes the lane `BLOCKED mutation: StrykerJS is not installed …` (or `cargo-mutants`), never a pass. Each mutant runs the change's issue's tagged tests. Each surviving mutant on a line a tagged test executes prints `SURVIVED <path>:<line>`, followed by its diff: the original line as `    -<text>` and the mutated line as `    +<text>` (four spaces, then the sign). No mutant on a line the change didn't add, or that no tagged test executes, is listed. A criterion whose tagged tests kill no mutant and whose criterion names no twin is `INVALID mutation: <ID>: its tests kill no mutant and name no planted wrong program`. A test with no twin that failed on the merge base before its assertion counts in the before lane once it kills a mutant in the same run. The lane writes nothing into the repository (Stryker's sandbox and reports go to a temporary folder). **On this machine** neither StrykerJS nor cargo-mutants is installed. The scratch repository links this checkout's `node_modules`, so the tests take the real result as required only when `node_modules/.bin/stryker` exists in this checkout; without it they require `BLOCKED mutation:` naming `StrykerJS`. Adding StrykerJS is a dependency the issue requires; adding it makes these tests demand the real result.
14. **Lifecycle tables and the enumerator.** No lifecycle table exists at the base, so this suite fixes their form: `packages/contracts/schemas/<object>.machine@<version>.json`, `{ "id": "lease.machine@1", "states": […], "initial": "<state>", "final": […], "moves": [{ "from", "event", "guard"?, "to" }] }`. The enumerator is the proof tool's own code, next to `scripts/proof.mjs`, over the tables of the repository checked; it needs no outside tool. It walks every state reachable from `initial`, and a reachable state from which no sequence of moves reaches a final state fails: `FAIL lifecycle: lease.machine@1: state stale has no move to a final state`, naming the table's ID. A table that holds prints `PASS lifecycle: <id>: …`. Locally it runs on the tables the change adds or modifies, and only then; at release on every table. The design's fuller enumeration (a small world of two sessions, two asks, one lease, crashes, orders of delivery) lands with the tables; the tests reach only the final-state rule the criterion names.
15. **The crash suite.** It runs locally when the change touches the hub core's storage interface: `packages/hub/src/vfs.ts` (the `Durable` interface that numbers each durable write point) or `packages/record/src/`. The suite is the files `tests/acceptance/16/crash*.test.ts`, today `crash-redraft.test.ts`, run with `node node_modules/vitest/vitest.mjs run --no-file-parallelism <files>` in the repository checked, with the run's environment; it prints `PASS crash: …` or `FAIL crash: …`. At release it runs whatever the change touched. The scratch repositories hold a stand-in at `tests/acceptance/16/crash-redraft.test.ts` that appends to the file `ACCEPTANCE_569_CRASH_MARKER` names, so a test sees whether the suite ran.
16. **The verdict replay.** It runs locally when the change touches `packages/verdicts/src/` (the verdict engine). Its cases are the change's `tests/fixtures/false-done/*.json` (the seeded false "done" cases) and `tests/fixtures/cheat/*.json` (the cheat corpus), each `{ "claim": <the engine's ClaimInput>, "expected": "<verdict>" }`. On each side, the merge base's temporary checkout and the change, it loads `packages/verdicts` through its `package.json` `exports` (a string, or `exports["."]`), after `npm ci` and the package's `build` script where the side has them, and calls `verdict(claim).outcome` for every case. Each case whose verdict differs prints `FAIL replay: <case path>: verdict <base> on the merge base, <change> on the change`, and the list ends with `FAIL replay: <k> differences need the maintainer's yes (list sha256:<64 hex>)`, a digest of the list. The yes is an approval (Reading 8) on the change's HEAD commit with the item `replay sha256:<that hex>`; with it the same lines print as `PASS replay: …`, and a yes on another digest, or signed by another key, changes nothing. The gate's check selection, the drafting job, the resolver's matching and the key fixture file have no code or file at the base (Contradictions), so no test reaches them.
17. **The environment.** `DEEP_PROOF_ISSUES` and `DEEP_APPROVERS` are read from the environment of whoever runs the preflight, never from the change. The tests set both for every run, unset `NODE_TEST_CONTEXT` so the lanes' own `node --test` runs report normally, and leave everything else as it is.

## Contradictions, gaps and what can't be proven here

- **No prerequisite for criteria 9 and 10 exists at the base.** There is no lifecycle table (`lease.machine@1` or any other), no enumerator, no seeded false "done" cases, no cheat corpus, no key fixture file, and no code for the gate's check selection, the drafting job or the resolver's matching. The crash suite exists (`tests/acceptance/16/crash-redraft.test.ts`) and the verdict engine exists (`packages/verdicts`). Readings 14 and 16 fix the table and case formats so the tests can plant them; the issues that land the real tables and corpora must use those formats, or this suite's redraft must follow them. The replay's subjects beyond the verdict engine are untestable until their code lands.
- **Criterion IDs.** The design says they are normalized "as open items are named" (NFC, case folded, trailing punctuation dropped), but every tag in the repo, and the issue's own wording ("the SHA-256 of its normalized text"), follows the trim-and-collapse command in `tests/acceptance/48/README.md`. Following the design would change every existing tag, so Reading 5 follows the repo.
- **"Fails the preflight" or INVALID.** The issue says the vacuous and wrong-reason fix tests fail the preflight; the design calls such a check INVALID. Reading 10 accepts either word on the before lane's line.
- **"Such a file".** The Scope says any removed or changed line "in such a file" counts, while criterion 3 lets an edit to a test no criterion tags pass. Reading 7 reads tests at the level of the test (with lines outside every test counting against the file's tagged tests) and goldens and fixtures at the level of the file.
- **"Approved by you".** The issue doesn't say how an approval is represented. Reading 8's signed tag is the representation the change under test can't forge; an approvals file, a commit trailer or a ref the change could create would let an agent approve its own edit.
- **Mutation tools.** StrykerJS and cargo-mutants aren't installed here, so criterion 8 and the mutant half of criterion 5 can only show BLOCKED on this machine until StrykerJS is a dev dependency. Rust mutation isn't reached at all: no criterion names a Rust case, and the tag convention for a Rust test (whose name can't hold `#`) is left to the implementer.
- **The design's import rule.** The design's trace lane also "refuses an acceptance test that imports the code under test by its path". No criterion of #569 asks for it, the planted tests here import by path as the repo's acceptance tests do, and adding the rule would fail them; it belongs to its own issue.

## Not covered

- A full local or release preflight: the tests record the lane commands `scripts/checks.mjs` would run, not the lanes themselves, which take tens of minutes.
- "Every lane runs locally, never on push or pull request": #246's workflows rule already fails any workflow file.
- The Proof's pasted output from real preflight runs.
